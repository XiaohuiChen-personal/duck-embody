1. One-screen overview: an LLM as its own SLAM

Duck Embody puts a frontier large language model (LLM) in charge of a 42 cm bipedal robot — the Open Duck Mini v2 — inside a simulated, unknown, duck-scale apartment, and asks it to complete one task: "Find the kitchen and walk to the counter." The model never touches motors directly. It issues tool calls (structured function invocations, the standard way LLM APIs let a model act on the world) such as turn_to_heading(90) or move(1.2); a harness translates those into velocity commands for a pretrained reinforcement-learning (RL) locomotion policy — a small neural network, trained by trial and error in simulation, that converts a desired walking velocity into 50-per-second joint commands that keep the biped upright and walking.

The unusual part is navigation. Robots normally localize with SLAM (Simultaneous Localization and Mapping): geometry pipelines that build a metric map from camera/LiDAR data and track the robot's pose within it. Duck Embody has no SLAM anywhere. The LLM is the sole holder of both the map and the position estimate:

  • It authors its own map as text — rooms, exits, landmarks — via memory tools (update_room, mark_exit, add_landmark), rendered back to it every turn in the MapGPT grammar ("Place N: <desc>" nodes plus explicit adjacency lines).
  • It tracks position by dead reckoning — integrating commanded velocity over time to estimate (x, y), the way a ship's navigator works without GPS. The estimate drifts honestly; ground truth is never shown.
  • It corrects drift cognitively via correct_position(x, y, reason) — recognizing a known landmark and resetting its own estimate. In SLAM terms this is loop closure (realizing you are somewhere you have been before and snapping the map back into consistency), performed by reasoning instead of geometry.

Why this is interesting. Anthropic's "How Claude Performs on Robotics Tasks" (Frontier Red Team, Jul 9 2026) found that current models "fail at tasks that require stable spatial memory, self-localization, or long open-loop plans." Duck Embody tests whether memory scaffolding changes that: the harness stores and re-injects a model-authored map, plan, and position estimate every turn, so failure can no longer be blamed on context loss — only on perception and reasoning. A prior-art sweep (2026-07-26, ~40 repos/papers) found the "LLM holds both map and position" slot unoccupied: MapGPT uses a text map but an oracle discrete graph; SG-Nav/SayNav have the LLM read a geometry-built scene graph; VLMnav is mapless and memoryless. source: AGENTS.md §1; article URL verified HTTP 200 (§10)

Locked: three models — Fable 5 (claude-fable-5), Opus 5 (claude-opus-5), GPT 5.6 sol — over N=4 fixed seeds (101–104), one frozen prompt/camera/tool config for all. Why: two Anthropic tiers mirror the paper's generational comparison, one cross-lab point; no per-model tuning keeps the comparison valid.

2. Three-layer architecture and the anatomy of one turn

The system is three layers with narrow interfaces. The SIM layer owns physics and rendering; the AGENT layer owns the LLM conversation, tools, and memory; the BENCHMARK layer owns trial orchestration, scoring, and reporting. Nothing in the agent layer touches Isaac Sim APIs directly, and nothing in the sim layer knows which model is playing.

One turn, end to end

A turn is one model-request/response cycle plus the motion it triggers. The numbered steps below match the circled numbers in the diagram:

  1. Render → observation payload. The harness renders one 512×512 RGB frame from the head camera on demand (rendering is decoupled from physics stepping so 50 Hz control does not pay a 50 Hz render cost) and assembles the observation: image, compass_deg — heading reported with the noise and precision of the robot's real IMU (inertial measurement unit — the orientation sensor, a BNO055 chip on the physical duck) — dead-reckoned position_estimate {x, y}, and status flags (bumped, fell, distance_moved_m), plus the re-injected memory block: the model's own map in MapGPT grammar, its carried-forward plan, trajectory line, and unexplored-exit list.
  2. LLM call — sim frozen. The payload goes to the provider API (Anthropic or OpenAI). Physics advances only inside env.step(), so however long the API takes, the robot is motionless and stable. source: AGENTS.md §5 "Pausing is safe"
  3. Model responds with a tool call — a motion macro (move, turn_to_heading, send_velocity), a memory write (update_room, mark_exit, correct_position, update_plan, …), another observation request, or declare_done().
  4. Clamp + execute. Motion commands are clamped to the policy's training hull (vx ∈ (−0.148, 0.222) m/s, vy ∈ (±0.111), wz ∈ (±0.5) rad/s) and run as a closed-loop macro: N = 50 × duration control steps at 50 Hz (the physics engine steps every 0.005 s and the policy acts once per 4 physics steps — "decimation 4" — giving 50 actions per simulated second), each injecting the velocity command and letting the RL policy produce joint targets. move auto-stops on collision and reports a bump; turn_to_heading closes the loop on the compass (±5° tolerance). source: parent isaac_lab_env/open_duck_mini_v2/env_cfg.py:189–190 (dt 0.005 s, decimation 4)
  5. Pause. Execution ends (target reached, bump, timeout, or duration elapsed) and the sim freezes again. The harness integrates the commanded velocity into the dead-reckoning estimate and updates status.
  6. Bookkeeping → next turn. The tool result is appended to the conversation; the turn and policy-second budgets are decremented; images older than K=10 turns are dropped (the memory block survives truncation). If a cap is hit or declare_done() was called, the stage ends and scoring runs; otherwise, back to step 1.
Memory principle (the line we never cross): the harness stores and formats; the LLM perceives, estimates, and decides. No geometric fact enters memory unless the model asserted it. The three declared sensor-realistic exceptions — compass heading, dead-reckoned position from commanded velocity, and closed-loop macros — mirror the real robot's IMU and command interface. Ground-truth position is never given to the model.

3. Why the simulator pauses while the model thinks

The locomotion policy consumes a velocity command every control step at 50 Hz source: parent env_cfg.py:189–190 (§10); a real-time world would therefore consume commands at 50 steps per wall-clock second, while a frontier-model API round trip (vision input, long context, tool schema) delivers roughly 0.2–0.4 decisions per second — an order-of-magnitude estimate, to be measured in the sanity episode (§11), but on any plausible value the gap exceeds two orders of magnitude. If the world kept moving during inference, every trial would mostly measure network latency and queue times: the duck would walk seconds past its intended stopping point, and the benchmark would compare API latencies rather than model capabilities.

So the sim pauses between LLM calls. This is safe by construction in Isaac Lab: physics advances only inside env.step(); not stepping means frozen, with no background integration source: AGENTS.md §5, verified against local Isaac Lab source 2026-07-26. This is the same protocol as Anthropic's robotics paper: it measures capability, not latency. The trade-off is honest and stated: results are an upper bound relative to a real-time deployment, where latency would add difficulty. Time-based metrics therefore count policy-seconds (simulated seconds of commanded motion), never wall-clock.

4. Process model: one simulator process, sequential trials

Isaac Sim runs on NVIDIA's Omniverse "kit" application framework; a cold start (extension loading, RTX renderer init, PhysX scene cooking) takes minutes on this machine. The DGX Spark also has a single GB10 GPU, and the parent project's hard-won rule applies: one Isaac Sim / GPU job at a time — a second kit process reliably dies during its init banner.

Locked: the entire batch (3 models × 4 seeds × up to 2 stages = up to 24 stage-episodes) runs inside ONE persistent Isaac Sim process (duck_embody/sim/session.py), with trials strictly sequential and an environment reset — not a process restart — between trials. Why: kit startup is minutes per launch and the one-GPU-job rule forbids parallelism anyway; a persistent session turns a multi-hour relaunch tax into seconds per trial.

Consequences of this choice:

  • The runner must be resumable. runner.py (today a docstring stub — §11) will record each completed trial's raw JSON as it lands in results/raw/; if the session dies mid-batch, restarting will skip completed trials rather than re-running them (re-running selected trials would be selection bias).
  • Reset hygiene matters. Between trials the env resets robot pose (to the seed's spawn point + heading), policy recurrent state (none — the actor is an MLP, but previous-action and gait-phase buffers reset with the env), dead-reckoning integrator, and the agent's conversation/memory. The apartment scene itself is static and persists.
  • Nothing else may touch the GPU. Writers, reviewers, and analysis scripts never launch kit processes while a batch could be live; scoring will expose --report-only-style paths that work from archived JSON without Isaac (also stubbed today — §11).

The policy being wrapped, v4_robust, is a PPO (Proximal Policy Optimization, the standard on-policy RL algorithm) policy trained with dynamics randomization. Its actor observes 59 dimensions of proprioception only — base angular velocity(3), projected gravity(3), velocity commands(3), joint positions(16), joint velocities(16), previous actions(16), gait phase(2); no base linear velocity, no vision. Observation normalization is baked into the model — inputs must never be pre-normalized again. 8. Trial lifecycle: spawn, caps, bumps, falls

A trial is one (model, seed) pair. The seed (101–104, identical set for every model) selects a spawn point and heading from the layout's spawn_points. Each trial contains up to two stages in the same episode:

  1. find_kitchen — success when the robot base is within 0.35 m of the kitchen-counter target region AND the model calls declare_done(). Declaring done in the wrong place scores as a failure with partial progress.
  2. return_home (continuation, only if stage 1 succeeded) — success when the base is within 0.5 m of the spawn point + declare_done(). This stage is the direct test of the map the model built: it must navigate back through territory it has only seen once.

Caps, per stage: 40 model turns and 240 policy-seconds of commanded motion. Hitting either cap ends the stage and is scored as a failure (with progress recorded). Capped or failed trials are never selectively retried — retrying only the bad ones is selection bias.

Bump vs. fall

BumpFall
What it isContact between the robot and a wall or furniture while walkingThe trunk tips past a tilt/height threshold — the robot is down
What happensmove auto-stops; status.bumped=true in the next observation; counted in metrics; trial continuesTrial ends immediately, scored as a failure with partial progress
WhyBumps are recoverable information ("there is a wall here") — for a blind-legged policy at duck scale they are part of normal explorationThe policy is 59-dim proprioceptive with no get-up skill: once down, the duck physically cannot recover, so continuing would be theater
The parent env's stock fall detector is trunk-contact-only (>1 N on trunk_assembly). In a furnished apartment that would misclassify a chest-high brush against a table as a fatal fall. The embody env replaces it: tilt/height defines a fall; object contact is demoted to a bump observation source: AGENTS.md §5 (fall detection gotcha). Exact thresholds are an open question (§11) pending the smoke tests.

9. Relation to Anthropic's embody harness (honest framing)

Duck Embody is inspired by, not derived from, Anthropic's "How Claude Performs on Robotics Tasks" (Frontier Red Team, Jul 9 2026) source: https://www.anthropic.com/research/claude-plays-robotics (HTTP 200, 2026-07-26). Their harness, safety-research/embody, is unreleased — the GitHub repo returns 404, verified today source: curl github.com/safety-research/embody → 404; api.github.com → "Not Found" (§10). Everything here is a from-scratch build: no code, prompts, or scenes were available to copy even if we wanted to.

What we deliberately keep from the paper's protocol: paused-sim tool-calling turns, egocentric frames, capability-not-latency framing, multi-model comparison on frozen configs, and the post-episode "quiz the model about its own map" idea (their explore-report pattern → our layout QA). What we deliberately change: a bipedal duck instead of a Unitree Go2 quadruped, an apartment search task with a two-stage return leg, and — the core contribution — the memory scaffolding their harness lacked: a model-authored persistent map, dead-reckoned position, and cognitive loop closure, re-injected every turn. Their headline failure mode (unstable spatial memory, self-localization, long open-loop plans) is exactly the variable this design isolates.

Honest limits, stated up front: N=4 seeds per model is a comparison, not a statistical claim (bootstrap CIs + full per-trial tables are always reported); paused sim is an upper bound on real-time performance; the sim-only result feeds — but does not prove — the parent robot project's Phase 5 (on-robot VLM) plans.

11. Open questions

  • Camera freeze pending smoke test. 90° HFOV at ~0.36 m is the plan, but the head-mount path is unresolved (the robot USD is instanceable; the head frame's forward axis is local −Z). scripts/smoke_camera.py must settle mount point and FOV BEFORE the config freeze.
  • Real achieved speed vs. commanded. Net displacement at vx=0.2 m/s was never measured in the parent repo (its metrics are instantaneous velocity errors). scripts/smoke_displacement.py must run before the 240 policy-second cap and dead-reckoning scale are trusted — if the duck achieves, say, 0.15 m/s, both need recalibration.
  • Fall-detector thresholds. Tilt/height numbers for the replacement fall termination are unspecified; they must be chosen so that normal gait oscillation and furniture bumps never trigger them.
  • Reset hygiene in one persistent process. Whether repeated env resets across ~24 stage-episodes leak state (PhysX warm-start caches, renderer memory growth) is unverified until the sanity episode runs back-to-back trials.
  • Policy artifacts not yet vendored. policy/ holds only the provenance README; copying model_2999.pt + yamls + ONNX (with checksums) is an open task on the critical path.
  • runner.py and scoring.py are docstring stubs. The resumability and offline re-scoring behaviors described in §4 are design intent, not implemented code; scoring must be unit-tested before any batch (hard rule).
  • providers/vllm.py is a dead stub. The locked model set (Anthropic + OpenAI only) removed the open-weight-VLM option, but the stub remains in the tree and AGENTS.md §7 still lists it; delete the file and update AGENTS.md §7 in the same commit.
  • docs/designs/index.html (the "all design docs" link target) now exists as a hand-written index of the six docs (reading order + canonical-constants quick reference, created 2026-07-26); it must be kept in sync as docs are added or retitled.
  • API-cadence figure. The 0.2–0.4 decisions-per-second API cadence in §3 is an order-of-magnitude estimate, not a measurement; the sanity episode should log real per-call round-trip times. (The other side of the comparison — 50 Hz control — is verified against parent env_cfg.py:189–190, §10.)
