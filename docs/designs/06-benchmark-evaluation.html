Benchmark Protocol & Scoring

Doc 06 - Duck Embody low-level design - 2026-07-26 - all design docs

APPROVED — owner-approved 2026-07-26. Deviations during implementation must update this doc in the same commit.

Who should read this / what you'll learn. This document defines how the Duck Embody benchmark is run and scored, assuming no prior robotics or simulation background. Duck Embody puts a large language model (LLM) in control of a simulated 42 cm bipedal robot inside an apartment it has never seen, with no mapping software — the model must build its own map as text, estimate its own position, and find the kitchen. This doc specifies: what the benchmark does and does not claim, exactly what is frozen before any trial runs (the fairness contract), the trial protocol, the per-trial log format, every metric with its exact formula, the statistics, the batch-runner design, cost/runtime estimates, the test gate that must pass before launch, and the deliverables. Every term of art (SPL, dead reckoning, loop closure, bootstrap CI, oracle path) is defined at first use.

1. What the benchmark claims — and does not claim

The benchmark compares three frontier models on identical tasks: Fable 5 (claude-fable-5, Anthropic), Opus 5 (claude-opus-5, Anthropic), and GPT 5.6 sol (OpenAI). Two Anthropic tiers give a generational comparison mirroring Anthropic's "How Claude Performs on Robotics Tasks" study (which compared Claude generations on the same robot harness); the OpenAI model adds one cross-lab data point. source: AGENTS.md §2 "Models" (locked 2026-07-26); https://www.anthropic.com/research/claude-plays-robotics

Locked: this is a feasibility case study of one maximum-scaffold memory configuration — the LLM-authored map, dead-reckoned position, and loop-closure tools are all ON for every model. It is not an ablation study. WHY: the question "can any frontier model do LLM-as-SLAM at all, given the best scaffolding we can build?" must be answered before "which scaffold component matters?" is worth asking. A no-memory ablation is the top stretch goal, not part of this benchmark.

What the benchmark does claim, if the data supports it: relative ranking of the three models on this task suite, under this one scaffold, in this one simulated apartment, with honest per-trial evidence published for every number.

What it does not claim:

  • No statistical significance claims. N=4 trials per model is far too small; we report ranking hypotheses with uncertainty intervals (§6).
  • No generality claims beyond this embodiment (one biped, one apartment, simulation only, one prompt, one camera config).
  • No claims about the unreleased original harness. Anthropic's safety-research/embody is unreleased (404 verified 2026-07-26); this is a from-scratch build of the paradigm, not a reproduction of their code.
  • No memory-scaffold causality claims — without the ablation, we cannot attribute success or failure to the scaffold itself.

2. The fairness contract: frozen before batch

A model comparison is only fair if every model faces byte-identical conditions. Everything below is frozen in a single git commit before the first batch trial, and the commit hash is recorded in every result file. If any frozen item changes, all prior trials are invalid and the batch restarts from zero.

3. Trial protocol

A trial is one model attempting the full episode from one seed. The matrix is 4 seeds × 3 models = 12 trials, run sequentially in one persistent Isaac Sim process. Isaac Sim (NVIDIA's physics simulator) takes minutes to start ("kit startup"), and the project's hard rule is one Isaac Sim / GPU job at a time on this machine — so the runner starts the sim once and resets the scene between trials rather than restarting the process. source: AGENTS.md §3 hard rule 1; runtime = DGX Spark, single GB10 GPU, headless, Isaac Sim 5.1.0-rc.19

3.1 Episode structure

  1. Reset. Robot is placed at the seed's spawn point and heading (from the layout's spawn_points); dead-reckoning integrator zeroed; memory empty; model context fresh.
  2. Stage 1 — find_kitchen. Task prompt: "Find the kitchen and walk to the counter." Success: robot base within 0.35 m of the kitchen-counter target region AND the model calls declare_done. Both conditions are required — physically arriving without declaring is a timeout, declaring elsewhere is a failure.
  3. Stage 2 — return_home. Continuation in the same episode (memory and context carry over): success = base within 0.5 m of the spawn point + declare_done. This is the direct test of whether the self-built map is real — the model must navigate back using only what it wrote down.

3.2 Caps and terminal conditions

ConditionLimitEffect
Model turns40 per stageStage scored as failure (with partial progress); episode continues to stage 2 only if stage 1 succeeded
Commanded motion240 policy-seconds per stageSame as turn cap. "Policy-seconds" = seconds of simulated time during which the locomotion policy executes commands; sim is paused while the model thinks, so this measures capability, not API latency (the paper's protocol).
FallanyEnds the trial — scored failure with partial progress. The biped can genuinely fall; that is part of the embodiment's difficulty.
Locked: timeouts and cap hits are scored as failures and are never selectively retried. WHY: retrying only the bad runs is survivorship bias; the only legitimate rerun is an infra failure (§7), which is logged as such.
The locomotion layer is deliberately not the thing under test: the pretrained v4_robust PPO policy has a clean record — 5/5 gait-validity gate, 0.00% falls over 3,200 push-free evaluation episodes — so falls in this benchmark are overwhelmingly attributable to navigation choices (collisions, wall-hugging), not to a wobbly walk. source: parent repo docs/jetson-mod/v4_comparison.md, v4_robust row (gait 5/5, fall rate 0.0) + per-condition fall table

4. Per-trial JSON log schema

One JSON file per trial, written incrementally (turn-by-turn flush, so a crash loses at most the in-flight turn). The log is the single source for scoring — the scorer never touches the simulator. Annotated schema:

  "config": {
    "freeze_commit": "<git sha>",        // fairness-contract commit (§2)
    "config_hash": "<sha256>",           // hash over frozen files; runner guard (§7)
    "model": "claude-fable-5",            // exact provider model ID
    "seed": 101,
    "spawn": {"xy": [x, y], "heading_deg": h}   // from layout spawn_points
  },
  "turns": [                              // one entry per model turn, both stages
    {
      "stage": "find_kitchen",            // or "return_home"
      "turn_idx": 7,
      "timestamp": "2026-07-27T04:12:31Z",
      "obs": {                            // what the model was shown (summary)
        "frame_paths": ["frames/t007_0.png"],   // saved camera frame(s)
        "compass_deg": 92.4,
        "position_estimate": {"x": 1.31, "y": 0.66},  // dead-reckoned, drifts
        "status": {"bumped": false, "fell": false, "distance_moved_m": 0.48}
      },
      "model_output": {
        "thought": "...",                 // model's visible reasoning text, if any

      },
      "execution": {                      // what the harness actually did
        "result": "moved 0.82 m, auto-stop on collision (bump)",
        "policy_seconds_used": 4.1,
        "pose_trace": [[1.02, 0.55], ...] // true base XY sampled every 10 control
                                          //   steps (5 Hz) during this turn's motion;
                                          //   scoring-only (never shown to the model),
                                          //   feeds the SPL path integral (§5.3)
      },
      "true_pose": {"x": 1.24, "y": 0.71, "heading_deg": 90.8},
      // ^ ground truth, logged EVERY turn for scoring — NEVER shown to the model

Gotcha: true_pose lives in the same file the scorer reads, but must never leak into the prompt path. The harness builds prompts exclusively from obs + memory_snapshot; a unit test asserts the rendered prompt contains no true_pose-derived values (the memory principle: ground-truth position is NEVER given to the model).

5. Metric definitions

All metrics are computed by duck_embody/scoring.py from the trial JSON plus the layout ground truth — nothing else (source: AGENTS.md §2 — the layout dict is simultaneously scene spec and scoring ground truth). Stage-level metrics are reported for find_kitchen; return_home gets its own SR/progress columns.

5.1 Success rate (SR). SR = successes / N per model per stage. A stage succeeds only if the distance condition (0.35 m kitchen counter / 0.5 m spawn) holds at the moment the model calls declare_done. WHY declare_done is required: the model must know it arrived; stumbling through the goal region does not demonstrate localization.
5.2 Progress. progress = clip(1 − d_final / d_initial, 0, 1), where d_initial is the straight-line distance from spawn to target at t=0 and d_final the distance at trial end (or at declare_done). There is no success override: successes report the same formula value as failures (naturally near 1.0, since success requires d_final ≤ 0.35 m), so every published progress number is reproducible from the canonical formula alone. WHY: gives partial credit on failures (a fall two steps from the counter ≠ a fall at spawn) and is clipped so wandering away from the goal cannot go negative. source: AGENTS.md canonical metrics — progress = 1 − d_final/d_initial clipped [0,1], no exceptions
5.3 SPL — Success weighted by Path Length. Per trial: SPL = S × l / max(p, l); reported as the mean over N trials, SPL = (1/N) Σᵢ Sᵢ · lᵢ / max(pᵢ, lᵢ) — the Anderson et al. 2018 SPL definition (later adopted as the ObjectNav convention by Batra et al. 2020, arXiv:2006.13171), verified verbatim against the paper. S is the binary success indicator (5.1); l is the oracle shortest path — the shortest collision-free path from the seed's spawn to the target, computed on the layout's free-space grid (the apartment floor minus wall/furniture footprints); p is the integrated true path length, p = Σ ‖pose(t+1) − pose(t)‖ over the sub-turn pose_trace samples (true base XY at 5 Hz during motion — §4 execution block). Sub-turn sampling matters: chord-summing only the once-per-turn true_pose entries would under-measure any within-turn curved motion (send_velocity arcs with wz ≠ 0, deflections during bumped move calls), shrinking p and inflating SPL. The max(p, l) denominator means SPL ≤ SR always: a successful but wandering trial scores below 1, and a failed trial scores 0. source: Anderson et al., "On Evaluation of Embodied Navigation Agents", arXiv:1807.06757, Eq. (1) — fetched 2026-07-26, HTTP 200 (see §11)
5.4 Time-to-kitchen. Cumulative policy-seconds (simulated seconds of commanded motion) from stage start to the successful declare_done; undefined (reported as "—", not a number) for failed trials. WHY policy-seconds and not wall-clock: the sim pauses while the model thinks, so wall-clock would measure API latency, not navigation efficiency.
5.5 Turns used. Model turns consumed in the stage (max 40). A proxy for deliberation cost, complementary to 5.4's motion cost.
5.6 Bumps and falls. bumps = count of collision events over the trial: auto-stops reported by move (per the canonical tool schema, move is the tool with collision auto-stop semantics) plus bumped = true collision reports surfaced in status for send_velocity commands (the raw escape hatch has no auto-stop clause in the canonical schema; its collisions are counted from the status report, one per command). falls ∈ {0, 1} (a fall ends the trial). Bumps measure how blindly the model drives; collision detection is part of the harness, so bumps are cheap but counted.
PINNED BY T3.2's review pass: the two sources above are the only two — turn_to_heading is deliberately excluded, even though a rotation in place can scrape furniture and the model is told about it via status.bumped (doc 04 §6.2). Counting rotations would not be a stricter measurement, it would be behaviour-dependent inflation: PolicyPlayback._bump_run is instance state that is not reset between calls, so after a bump-stopped move the debounce counter already sits at its threshold and the first control step of the recovery turn re-flags bumped. Bump-then-turn-away is the canonical recovery pattern, so a model that turns while still in contact would score worse on this published metric than one that reverses with send_velocity, for the same number of real collisions. tools.ToolContext.bumps implements exactly the two sources named above and is trial-scoped: reset_for_stage() leaves it alone (doc 05 §4.1), because "over the trial" in the first sentence spans both stages while doc 05 §3.3 resets only turns and policy-seconds.
5.7 Map accuracy. Scored against the layout ground truth in two parts.
Room-node precision/recall. The model's claimed rooms (its update_room entries) are matched to true rooms. Matching rule: a claimed room matches a true room iff (a) its name is similar (case-insensitive match after synonym normalization from a fixed, frozen synonym table — e.g. "lounge"→"living_room"; no fuzzy embedding matching) AND (b) its evidence places it in the true room's polygon — evidence = the true pose at the moments the model called set_current_room/update_room for it, or the true positions of its claimed landmarks; majority of evidence points must fall inside the polygon. Each claimed room may match at most one true room and vice versa (greedy one-to-one matching in order of evidence count; ties broken by name-similarity first, then by earliest claim time). Then precision = matched / claimed, recall = matched / true_rooms_visited (recall counts only rooms the robot actually entered per the true trace — the model cannot be penalized for not mapping rooms it never saw). Edge convention: if the model never claims a room (claimed = 0), precision is undefined — reported as "—" and excluded from the aggregate mean, never coerced to a number; recall is then 0 whenever at least one room was visited.
Adjacency edge accuracy. The model's exits with status leads_to:<room> define claimed edges between matched rooms; accuracy = correct claimed edges / all claimed edges, checked against the layout adjacency graph. Unexplored exits are excluded (claiming "there's an unexplored exit north" is not an adjacency assertion).
5.8 Dead-reckoning drift. drift = ‖position_estimate − true_pose‖ at the moment of declare_done (per stage), plus the count of correct_position calls and the magnitude of each correction (‖old estimate − new estimate‖). WHY both: final drift measures how honest the estimate ended up; the corrections series shows whether the model actively did cognitive loop closure (recognizing a place and snapping its estimate) or just rode the drift. Dead reckoning = integrating commanded velocity over time to estimate position; it drifts because the real robot slips, bumps, and turns imperfectly.
5.9 Layout QA. After the episode ends, the model is asked 5 fixed questions in a fresh exchange where it sees only its own final map/memory block — no new camera frames, no sim access. Each answer is scored 0 / 0.5 / 1 against the layout ground truth (+ the logged true trace for "visited" questions); QA score = mean of the five. The questions and rubrics are frozen with the prompt template:
#Question (exact text)Rubric (1 / 0.5 / 0)
1"Which room connects the bedroom to the kitchen?" 1: names the unique connector room (per adjacency graph). 0.5: names a room that is adjacent to exactly one of the two. 0: anything else.
2"Starting at the front of the sofa, give turn-by-turn directions to the fridge." 1: room sequence matches the oracle route AND initial direction correct AND ends at the fridge. 0.5: correct room sequence but a wrong/missing turn direction, or correct directions with one wrong room name. 0: route would not reach the kitchen.
3"How many rooms did you visit? Name them." 1: count and names match the true visited set (from the true trace ∩ room polygons). 0.5: names correct but count off by one, or one room missing/extra. 0: otherwise.
4"Which direction (compass) is the kitchen from your spawn point?" 1: matches the true bearing bucketed to 8-way compass (spawn → kitchen centroid). 0.5: adjacent bucket (e.g. E vs NE). 0: otherwise.
5"Name one landmark in each room you visited." 1: a true layout landmark for every visited room. 0.5: correct for all but one room. 0: otherwise.
All five ground-truth answers were verified computable from the layout dict + the logged true trace alone (no extra sim queries): connector room = unique common neighbor in the adjacency graph; directions = breadth-first search room path + bearings; visited set = true trace ∩ room polygons; kitchen bearing = spawn → centroid, 8-way bucketed; landmarks = per-room layout lists. See §11 for the executed check.

6. Statistics

Every metric is reported as mean ± bootstrap 95% confidence interval over the N=4 trials. The bootstrap: resample the 4 per-trial values with replacement 10,000 times, compute the mean of each resample, and take the 2.5th and 97.5th percentiles as the interval. (A confidence interval is a range that expresses how much the mean could plausibly move under resampling — with N=4 it will be wide, and showing that width is the point.)

Honesty clause. N=4 supports ranking hypotheses ("Fable 5 looked stronger than GPT 5.6 sol on SPL in this suite"), not significance claims. With 4 trials, one lucky seed moves a success rate by 25 percentage points. Therefore: (a) the per-trial table is always published alongside any aggregate; (b) no "statistically significant" language anywhere; (c) overlapping CIs are reported as "indistinguishable at this N"; (d) no claims beyond the data.
Locked: bootstrap with 10,000 resamples, fixed RNG seed for the bootstrap itself (so the reported CIs are reproducible), and percentile method (not BCa). WHY: at N=4 the sophistication of the interval method is noise; reproducibility is not.

7. Runner design

The batch runner (duck_embody/runner.py + scripts/run_trial.py) executes the 12-trial matrix. Design requirements:

  • Sequential, one sim process. Trials run one at a time inside the single persistent Isaac Sim process (§3). The runner never launches a second kit process.
  • Resumable by trial id. Before running a trial, the runner checks results/<trial_id>.json: if the file exists AND is complete (has a final block that validates against the schema), the trial is skipped. A partial file (crash mid-trial) is moved to results/incomplete/ with a timestamp suffix and the trial reruns.
  • Config-hash guard. At startup the runner recomputes the hash over the frozen files (§2) and compares it to the config_hash in every existing result it would resume around. Mismatch ⇒ hard refuse with a message naming the changed file. There is deliberately no --force flag; the correct responses are "revert the change" or "start a new batch directory".
  • Infra failure vs model failure. A trial that ends by cap, fall, or wrong declare_done is a model failure — final, never rerun. A trial that ends because the harness broke (sim crash, provider 5xx/429 exhaustion after backoff, camera returning black frames, scoring-input corruption) is an infra failure: the partial JSON is preserved in results/incomplete/, an entry is appended to results/rerun_log.md (trial id, timestamp, cause, evidence path), and the trial reruns from scratch. The rerun log ships with the results — reruns are visible, not silent.
  • API keys via env vars only (ANTHROPIC_API_KEY, OPENAI_API_KEY); never in configs or logs.
Gotcha: the infra/model distinction is the integrity-critical judgment call. The rule: if the model could in principle have avoided it, it is a model failure. A bump-stop is model; a segfault is infra. A provider timeout on one turn is retried at the API-call level (bounded backoff) without consuming a model turn — only unrecoverable provider failure escalates to infra-rerun.

9. Test plan (the pre-batch gate)

Locked: tests/test_scoring.py and tests/test_layout.py MUST pass before any batch trial launches — non-negotiable gate. WHY: scoring bugs found after the batch invalidate paid, hours-long runs; the scorer is pure-Python over JSON + the layout dict, so it is fully testable without Isaac Sim (and the test suite must never launch a kit process).

9.2 tests/test_layout.py

  • Room polygons are non-overlapping and lie within the 4.8 × 3.6 m apartment bounds.
  • Every doorway (0.35 m wide) connects exactly the two rooms the adjacency graph says it does, and is reachable on the free-space grid (duck body ~0.16 m fits).
  • The target region lies inside the kitchen polygon.
  • An oracle path exists on the free-space grid from every seed spawn (101–104) to the kitchen target, and back (for return_home's scoring).
  • Every seed spawn (101–104) lies well outside the kitchen-target goal radius — assert spawn-to-target distance > 3 × 0.35 m — so d_initial > 0 (progress and SPL denominators are well-defined, §5.2/§5.3) and stage 1 can never be trivially successful at spawn.
  • The 5 QA ground-truth answers are computable and unique — in particular exactly one room connects bedroom and kitchen (Q1's uniqueness precondition).
