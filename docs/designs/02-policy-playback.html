Who should read this / what you'll learn. This doc is for anyone implementing or reviewing the layer of Duck Embody that makes the robot's legs work: how we load a pretrained walking controller (a neural network trained with reinforcement learning), how we feed it velocity commands chosen by an LLM, and how we reconfigure the training environment so it behaves like a single persistent apartment instead of a 4,096-robot training farm. No robotics or Isaac Sim background is assumed — every term of art is defined on first use. The commanding LLM harness itself (tools, memory, scoring) is covered in doc 05 (agent harness) and doc 06 (benchmark & scoring); here we stop at the boundary "the harness asks for (vx, vy, wz) for N steps" and go downward from there.

1. The trained policy: v4_robust

What a locomotion policy is. The Open Duck Mini v2 is a 42 cm bipedal robot with 16 actuated joints. Walking is controlled by a policy: a small neural network (MLP, hidden layers 512/256/128) that runs at 50 Hz, reads a 59-number snapshot of the robot's state (the "observation", section 2), and outputs 16 joint-position targets. It was trained with PPO (Proximal Policy Optimization, a reinforcement-learning algorithm) — the network learned to walk by trial and error across 4,096 simulated robots in parallel source: parent isaac_lab_env/open_duck_mini_v2/env_cfg.py:185 (self.scene.num_envs = 4096). Duck Embody does zero training: we play back this frozen network and let an LLM choose the velocity commands it tracks.

Provenance. The policy is v4_robust, trained in the parent robot project (Open_Duck_Mini_Jetson, branch v2) with RSL-RL (a lightweight GPU PPO implementation) on the corrected layout-v2.1 robot model. Checkpoint:

~/IsaacLab/logs/rsl_rl/open_duck_ppo_robust/2026-07-07_00-15-43/model_2999.pt

(vendored into this repo's policy/ directory so the public repo is self-contained; see open questions). It was trained with an asymmetric actor/critic: the critic (value network, training-only) sees 62 dims including true base linear velocity; the actor (the deployed network) sees only 59 dims, because the real robot's IMU cannot measure linear velocity source: agent.yaml obs_groups: {actor: [policy], critic: [critic]}, ~/IsaacLab/logs/rsl_rl/open_duck_ppo_robust/2026-07-07_00-15-43/params/agent.yaml lines 6–10. Training included dynamics domain randomization (random pushes, mass/CoM/friction perturbations) source: parent env_cfg.py:278–346 (OpenDuckRobustEnvCfg).

Why we trust it. Under the parent project's evaluation protocol (3,200 episodes: 5 command conditions × 10 windows × 64 envs, 30 s each, deterministic, seed 42), v4_robust scored a 5/5 gait-validity gate and 0.00% falls, plus a passing manual video audit source: parent docs/jetson-mod/v4_comparison.md line 62 (v4_robust row: gate 5/5, falls 0.0) and line 70 (0.0 falls in all five conditions). Caveat for our use case: those numbers are push-free, flat-ground, fixed-command 30 s windows — see section 7 for the regimes our project enters that the eval never touched.

Locked: v4_robust (model_2999.pt, run 2026-07-07_00-15-43) is the only locomotion policy in Duck Embody. WHY: it is the parent project's deployment mainline with the cleanest measured record on the current robot model, and freezing one policy keeps the LLM comparison fair.

2. The 59-dim observation contract

Every control step, the environment assembles this vector and the policy returns 16 actions. The source of truth is the training run's own config dump (params/env.yaml in the checkpoint directory) — not any document, including this one. Order matters; the concatenation is:

#NameDimsMeaningenv.yaml func (params/env.yaml line)
1base_ang_vel3Trunk angular velocity in body frame (gyro)mdp.observations:base_ang_vel :365
2projected_gravity3Gravity direction in body frame (tilt sense)mdp.observations:projected_gravity :378
3velocity_commands3Commanded (vx, vy, wz) — what the LLM controlsmdp.observations:generated_commands :391
4joint_pos16Joint angles relative to default pose (rad)mdp.observations:joint_pos_rel :401
5joint_vel16Joint velocities (rad/s)mdp.observations:joint_vel_rel :414
6actions16Previous action vectormdp.observations:last_action :427
7gait_phase2[cos, sin] of the reference gait cycle phaseimitation_reward:gait_phase_observation :437
Total59No base_lin_vel — that is critic-only (62 dims, env.yaml :452+)
Normalization is baked in — never pre-normalize. The checkpoint was trained with obs_normalization: true on both actor and critic MLPs source: params/agent.yaml lines 30, 42, and RSL-RL's get_inference_policy() returns a callable that applies the learned running mean/std internally. Feed it raw environment observations. Normalizing upstream would double-normalize and produce garbage actions that look almost plausible — the worst kind of bug.
The gait_phase trap. Dims 58–59 come from gait_phase_observation(), which does not own its phase counter. The counter (_step_idx) lives inside the ImitationReward reward term and is advanced once per step by the reward computation; the observation function merely looks the reward instance up in a module-global registry (_instances: dict[int, ImitationReward]) keyed by id(env), and returns zeros if no instance is registered source: parent isaac_lab_env/open_duck_mini_v2/imitation_reward.py:45 (registry), :154 (registration in the term's __init__), :290 (counter advance inside the reward call), :295–308 (observation reads the registry, zero-fallback). Consequence: if you strip the reward manager or remove the imitation reward term ("we're not training, who needs rewards?"), 2 of 59 obs dims silently freeze at zero and gait quality degrades with no error message. Design: DuckEmbodyEnvCfg keeps the full reward manager computing every step. The reward values are discarded; the side effect is what we need. The wasted compute is irrelevant at num_envs=1.

3. Policy loading design

We follow the proven adapter from the parent repo's evaluation harness (RslRlPolicy, parent scripts/evaluate_policies.py:1205–1255) rather than inventing a loader:

# duck_embody/policy_io.py (design)
from importlib import metadata
from rsl_rl.runners import OnPolicyRunner
from isaaclab_rl.rsl_rl import RslRlVecEnvWrapper, handle_deprecated_rsl_rl_cfg
from isaaclab_tasks.utils.parse_cfg import load_cfg_from_registry

agent_cfg = load_cfg_from_registry(TASK_ID, "rsl_rl_cfg_entry_point")
agent_cfg = handle_deprecated_rsl_rl_cfg(agent_cfg, metadata.version("rsl-rl-lib"))  # REQUIRED
env_w   = RslRlVecEnvWrapper(gym_env, clip_actions=agent_cfg.clip_actions)
runner  = OnPolicyRunner(env_w, agent_cfg.to_dict(), log_dir=None, device=agent_cfg.device)
runner.load(CHECKPOINT_PATH)
policy  = runner.get_inference_policy(device=env_w.device)  # deterministic MEAN actions
  • The shim is not optional. rsl-rl-lib 5.x renamed config keys; loading our config without handle_deprecated_rsl_rl_cfg crashes OnPolicyRunner with KeyError: 'class_name' source: parent scripts/evaluate_policies.py:1208–1210 (docstring), :1219–1221 (shim call + comment), :1176 (version lookup); installed rsl-rl-lib is 5.0.1.
  • Deterministic inference. get_inference_policy() returns mean actions (no sampling noise) with normalization applied — same mode as the 3,200-episode eval record, so playback behavior matches the evidence we trust source: evaluate_policies.py:1230–1231.
  • torch.no_grad(), NOT torch.inference_mode(). Stepping the env inside inference_mode marks lazily-created sim-state tensors as inference tensors; a later out-of-scope env.reset() (we reset between trials!) then fails with "Inplace update to inference tensor outside InferenceMode" source: evaluate_policies.py:1446–1450 (comment + no_grad block). All Duck Embody stepping loops use no_grad.
Locked: load via OnPolicyRunner + deprecation shim + get_inference_policy, step under torch.no_grad(). WHY: byte-for-byte the pattern already validated by 3,200 eval episodes in the parent repo; novelty here buys only risk.

4. Command injection — the core mechanism

This is the single most important (and most booby-trapped) piece of the playback layer. The environment inherits Isaac Lab's UniformVelocityCommand term, which was designed to generate random training commands — three of its behaviors will silently fight an external commander:

TrapWhat it doesEvidence
Heading controller overwriteWith heading_command=True (the inherited default) and rel_heading_envs=1.0, _update_command() recomputes wz every step from a P-controller on a random heading target — any wz you wrote is clobbered before the policy sees it. IsaacLab velocity_command.py:143–159 (heading branch writes vel_command_b[env_ids, 2]); defaults heading_command=True, rel_heading_envs=1.0 at velocity_env_cfg.py:98–99
Standing-env zeroingrel_standing_envs=0.02: on each resample the env has a 2% chance to be flagged "standing", after which _update_command() zeroes the whole command every step. velocity_command.py:141, :162–163; default 0.02 at velocity_env_cfg.py:97
10 s resamplerresampling_time_range=(10.0, 10.0): every 10 s the term draws a fresh random command from cfg.ranges, discarding whatever was in vel_command_b. scheduler: command_manager.py:161–163, :184 (CommandTerm.compute decrements time_left, redraws it from resampling_time_range); redraw itself: velocity_command.py:130–141; default at velocity_env_cfg.py:96

The parent repo already solved the fixed-command version of this problem in apply_condition() source: parent scripts/evaluate_policies.py:1386–1416, whose docstring notes the key fact that makes the design safe: the live term reads cfg.ranges / cfg.heading_command / cfg.rel_standing_envs dynamically on every resample, so mutating the cfg on a built env works. Our design extends it for per-turn command changes:

# One-time, at env build (defuse the traps):
term = env.command_manager.get_term("base_velocity")
term.cfg.heading_command    = False        # heading P-ctrl can never overwrite wz
term.cfg.rel_standing_envs  = 0.0          # no random standing zeroing
term.cfg.resampling_time_range = (1.0e9, 1.0e9)   # resampler effectively never fires

# Per LLM-commanded segment (belt AND suspenders):
def set_command(term, vx, vy, wz):          # values pre-clamped to the training hull
    term.cfg.ranges.lin_vel_x = (vx, vx)    # belt: IF anything ever resamples,
    term.cfg.ranges.lin_vel_y = (vy, vy)    #   it can only redraw the same value
    term.cfg.ranges.ang_vel_z = (wz, wz)
    term.vel_command_b[:, 0] = vx           # suspenders: take effect immediately,
    term.vel_command_b[:, 1] = vy           #   no waiting for a resample event
    term.vel_command_b[:, 2] = wz

The direct vel_command_b write is safe precisely because of the one-time defusal: with the heading branch off and standing fraction 0, _update_command() becomes a no-op source: velocity_command.py:143–163 — both mutation sites are gated on cfg.heading_command and the standing mask, and with the resample interval pinned to ~31 years of sim time the redraw never triggers within a 240-policy-second stage. The degenerate ranges are retained anyway so that an env reset (between trials, which does resample all envs) also deals the intended command. All commands are clamped to the training hull vx ∈ (−0.148, 0.222), vy ∈ (−0.111, 0.111), wz ∈ (−0.5, 0.5) m/s / rad/s before injection source: parent env_cfg.py:215–217 (training ranges).

Locked: defuse-once + pin-ranges + direct-write per segment. WHY: it is the parent repo's proven apply_condition pattern, extended with the direct buffer write so per-turn command changes take effect on the very next control step instead of the next resample.

Auto-reset is the sneakiest failure mode in this table. Isaac Lab manager-based envs reset any env whose termination manager reports done, inside the same env.step() call, and return the post-reset observation. With the stock PLAY config a Duck Embody trial would hit time_out at 40 s and the robot would be teleported to a random pose near the env origin — reset_base redraws xy in ±0.5 m and yaw in ±π (this table's own reset_base row) — or to exactly the pinned spawn once DuckEmbodyEnvCfg's degenerate ranges are set. Either way, no exception is raised — dead-reckoning, the LLM's map, and scoring would all silently corrupt. Hence time_out=None and harness-side cap enforcement.

6. Motion macros: turn_to_heading, move, send_velocity

The LLM does not micro-manage 50 Hz control. It calls three motion tools, each of which runs a closed-loop (or fixed-duration) stepping loop over the frozen policy. Shared math: control runs at 50 Hz (sim.dt=0.005 s × decimation 4 source: parent env_cfg.py:189–190), so duration_s maps to N = round(50 × duration_s) control steps. Commands are injected via section 4's set_command(); every loop iteration checks the fall flag and the bump sensor. "Dead reckoning" = estimating position by integrating commanded velocity over time; it drifts, and that drift is a measured feature of the study, not a bug to hide.

6.1 turn_to_heading(heading_deg)

def turn_to_heading(heading_deg, tol_deg=5.0, timeout_s=8.0):
    target = wrap_to_pi(deg2rad(heading_deg))
    for _ in range(int(50 * timeout_s / CHUNK)):        # CHUNK = 10 steps = 0.2 s
        err = wrap_to_pi(target - compass_rad())        # compass: BNO055-realistic heading
        if abs(err) <= deg2rad(tol_deg):
            set_command(0, 0, 0); step(CHUNK)           # settle
            return ok(turned_to=heading_deg)
        wz = clip(KP_TURN * err, -0.5, +0.5)            # P-control, clamped to hull
        set_command(0, 0, wz); step(CHUNK)
    return timeout(final_heading=compass_deg())

KP_TURN initial value 1.5 (saturates at 0.5 rad/s for errors > ~19°, proportional inside); tuned once during the smoke test, then frozen. This mirrors Isaac Lab's own heading controller structure (P-gain then clip to ranges.ang_vel_z) source: velocity_command.py:153–159, stiffness 0.5 at velocity_env_cfg.py:100 — we just point it at the LLM's target instead of a random one.

6.2 move(distance_m)

def move(distance_m):
    dist    = min(distance_m, 1.5)                      # cap per call
    goal_s  = dist / 0.2                                # commanded vx = 0.2 m/s
    for chunk in range(int(50 * goal_s * 1.5 / CHUNK)): # 1.5x time margin
        wz = clip(KP_HEADING * heading_error(), -0.5, +0.5)   # HOLD heading (T1.3)
        set_command(0.2, 0, wz); step(CHUNK)
        integrate_dead_reckoning(vx=0.2, dt=0.2)        # NO k — commanded velocity only
        if bumped():                                     # trunk contact force sustained
            set_command(0, 0, 0); step(CHUNK)
            return stopped(reason="bump", moved=dr_distance())
        if dr_distance() >= dist:
            set_command(0, 0, 0); step(CHUNK)
            return ok(moved=dr_distance())
    return timeout(moved=dr_distance())
MEASURED (T1.3, 2026-07-26) — three corrections to this section.
  • k = 1.004 (4.018 m achieved vs 4.0 m commanded over 20 s; measured speed 0.201 m/s). The feared systematic shortfall does not exist on flat ground.
  • The integrator uses commanded velocity with NO k. The pseudocode comment above previously read x += k*0.2*0.2*cos(h); that is now corrected. AGENTS.md rule 5 wins: dead reckoning must drift honestly, because noticing and correcting that drift is the capability under test. k is consumed only by time-cap/wall-clock forecasting and by the move() servo target (dist / k) and its timeout margin.
  • move() must HOLD HEADING. Commanded straight, the bare policy yaws about 1.8 °/s — 36.6° over 20 s / 4 m, ~103° per 100 s on the 120 s hold. (Consistent with the parent eval's own wz error of 0.067 rad/s = 3.8 °/s, so this is a property of the policy, not a harness bug.) Open loop, a 1.5 m move aimed at a 0.35 m doorway would end ~0.18 m off course. Closing wz on the compass during the drive (KP_HEADING 1.5, corrected every 0.2 s) reduces drift to 0.39° over the same 20 s / 4 m with k unchanged at 1.018. This is squarely inside AGENTS.md rule 5's declared exception (c), closed-loop motion macros servoing on compass + dead reckoning. source: results/figures/smoke/displacement_report.json (runs a, d, f)
AMENDED by the pre-freeze forensic pass — a fall during the trailing settle chunk is a fall. Both macros append a trailing 0.2 s zero-command settle chunk (the step(CHUNK) after set_command(0,0,0) above) and merge it into the result — but both decided their stop_reason before that chunk ran, so a robot that toppled while stopping was recorded as fell: true with stop_reason: "reached"/"timeout" and stopped_early: false; turn_to_heading additionally derives the model-facing timed_out from that string, so the very command that ended the trial could tell the model it merely timed out. Fixed in both macros (if settle.fell: reason = "fell"), pinned by tests/test_execute_ordering.py. Related merge-layer rules — the shared merge_exec_results, the first-seen-order union of contact_groups across chunks, and the call-accumulated fall_diagnostics.policy_seconds_into_call — are recorded in doc 06 §4's widened list.

Bump detection reads the existing contact sensor (the same signal the removed base_contact termination used), debounced over a few chunks so a single 1 N grazing spike doesn't halt a legitimate squeeze through a 0.35 m doorway.

6.3 send_velocity(vx, vy, wz, duration_s)

def send_velocity(vx, vy, wz, duration_s):
    vx, vy, wz = clamp_to_hull(vx, vy, wz)              # section 4 hull
    d  = clip(duration_s, 0.2, 3.0)
    set_command(vx, vy, wz); step(round(50 * d))
    set_command(0, 0, 0)                                 # never leave a command running
    integrate_dead_reckoning(vx, vy, wz, d)
    return status()

Raw escape hatch for the LLM (e.g. backing out of a corner with vx < 0). Every macro ends by zeroing the command — the sim pauses between LLM turns, and a nonzero command must never be left armed across a multi-minute LLM think.

CORRECTED BY T3.2 (AGENTS.md rule 5): the last line integrates an ARC, not a chord — and the [0.2, 3.0] clip lives in tools.py. integrate_dead_reckoning(vx, vy, wz, d) above is one call at one heading, which is wrong for the only tool that can translate and rotate at once. send_velocity(0.222, 0, 0.5, 3.0) sweeps 86° while travelling 0.67 m, so integrating the whole command along the start heading misplaces the estimate by ~0.45 m — larger than the 0.35 m find_kitchen success radius, and it is the harness's arithmetic rather than the robot's slip, which is exactly the distinction PLAN T3.2 (b) exists to protect. memory.PositionIntegrator.integrate_arc() instead advances the heading by degrees(wz) × CONTROL_DT per control step from the commanded wz — no sensor read, nothing measured, and identical to integrate() step for step when wz = 0. The compass is re-read before the next command, so the measured commanded-vs-realised yaw gap (T1.3: 0.982) never accumulates across calls.

Two further notes on this pseudocode as implemented: the clip(duration_s, 0.2, 3.0) is not in PolicyPlayback.execute() — it is tools.DURATION_RANGE_S, applied before the call and echoed to the model like every other clamp (doc 05 §4.2) — and the duration fed to the integrator is ExecResult.policy_seconds, never d, so a command cut short by a fall does not walk the estimate on without the robot.

7. Known unknowns

Honesty section: things the parent repo's evidence does not cover, with our mitigation.

  • Net displacement was never measured. The parent eval's velocity metric is an instantaneous L2 error between commanded and achieved velocity (v4_robust: 0.153 m/s source: v4_comparison.md line 62, v_xy err column) — it never integrated position. Commanded 0.2 m/s could realize as ~0.17 m/s net and the eval would not distinguish "tracks with small symmetric noise" from "tracks with a consistent shortfall" — and a mean L2 error of 0.153 m/s against commands of ~0.2 m/s magnitude leaves plenty of room for exactly such a shortfall. Dead reckoning built on commanded velocity inherits that unknown bias. Mitigation: smoke_displacement.py (harness smoke test, runs in the one persistent Isaac Sim process) drives fixed forward/turn segments, measures ground-truth displacement, and calibrates the realization factor k and expected drift rate — before the caps, scoring constants, and prompt are frozen.
  • Long constant-command holds are untested. Eval episodes held one command for 30 s; a Duck Embody stage allows up to 240 policy-seconds with commands held across many macro calls. Slow instabilities (thermal-like drift in gait phase alignment, yaw creep) would be invisible in the record. Mitigation: smoke test includes a 120 s straight-line hold.
  • Step command changes are untested. Training resampled commands every 10 s with the env mid-gait; eval never switched commands inside a window. Our macros switch commands every 0.2 s chunk (turn P-control) and at every macro boundary. The policy's previous-action and gait-phase obs should absorb this, but "should" is not evidence. Mitigation: smoke test includes turn→drive→turn transitions and watches for stumbles.
  • Apartment terrain ≠ eval terrain. Eval was an empty plane; doorway squeezes and prop contact are new. Falls there are scored honestly as falls (a fall ends the trial), and bump counts are a reported metric.

9. Validation performed
