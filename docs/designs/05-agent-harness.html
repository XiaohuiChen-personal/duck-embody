This document is the low-level design of the agent harness: the loop that lets a large language model (LLM — a text-and-image model such as Claude, called over an API) drive a simulated 42 cm bipedal robot through an unknown apartment using tool calls (structured function invocations the model emits instead of prose). 1. The core question: can an LLM be its own SLAM?

Anthropic's "How Claude Performs on Robotics Tasks" (Frontier Red Team, Jul 9 2026) reported a consistent negative finding: models navigating a quadruped from egocentric camera frames struggled with spatial memory — they re-explored visited areas, lost track of where they were, and leaned heavily on whatever was in the recent context window. Their harness (safety-research/embody) is unreleased source: 404 verified 2026-07-26, per AGENTS.md §1, and it deliberately provided little memory scaffolding. Duck Embody asks the follow-up question: if we give the model a well-designed externalized memory — but make the model itself author every fact in it — can it navigate an unknown apartment reliably? That is, we replace SLAM (defined below) with the model's own cognition plus a text notebook the harness faithfully re-displays.

Boundary principle (locked): "The harness stores and formats; the LLM perceives, estimates, and decides." No geometric fact enters memory unless the model asserted it from its own observations. WHY: the moment the harness starts injecting ground truth (real positions, real room labels, a geometry-built graph), the benchmark stops measuring the model's spatial cognition and starts measuring our scaffolding. Three declared, sensor-realistic exceptions mirror what a real robot's hardware provides for free: (a) compass heading (the BNO055 IMU on the physical duck gives absolute yaw), (b) dead-reckoned position integrated from commanded velocity (drifts honestly — commanded ≠ actual), and (c) closed-loop motion macros (turn_to_heading, move) that servo on those same two signals. Ground-truth position is never given to the model. source: AGENTS.md §3 rule 5

2. SLAM for newcomers — what we keep, replace, drop

SLAM (Simultaneous Localization And Mapping) is the classical robotics answer to "where am I, and what does this place look like?". A SLAM system provides three services: localization (a running estimate of the robot's pose — position + heading), mapping (a persistent model of the environment, e.g. an occupancy grid or landmark graph), and loop closure (recognizing "I've been here before" and snapping the accumulated pose error back to the earlier estimate). Under the hood it does heavy geometry: probabilistic filtering, bundle adjustment, uncertainty propagation over thousands of raw sensor readings.

We keep the three services but re-implement each as language, and drop the geometric machinery — a deliberate mirror of the "keyframe" philosophy in visual SLAM (keep a sparse set of informative snapshots, discard the raw stream):

SLAM serviceClassical implementationDuck Embody implementationKeep / replace / drop
LocalizationFilter fusing odometry + visionHarness integrates commanded velocity into an (x, y) estimate (dead reckoning — declared exception); compass gives headingKeep as breadcrumb position log
MappingOccupancy grid / feature mapModel-authored room / exit / landmark graph stored as text, rendered back every turnReplace: landmark memory as language
Loop closurePlace recognition + pose-graph optimizationModel re-recognizes a landmark and calls correct_position(x, y, reason) — cognitive loop closureReplace: cognition instead of optimization
Geometric optimizationBundle adjustment, pose-graph solvers—Drop
Uncertainty propagationCovariance tracking— (the model is told the estimate drifts; no numeric covariance)Drop

3. Episode loop design

One trial = one seed (101–104; seed selects spawn point + heading from the layout's spawn_points) × one model, run inside the single persistent Isaac Sim process source: AGENTS.md §3 rule 1 (one GPU job; kit startup is minutes). A trial contains up to two stages: find_kitchen ("Find the kitchen and walk to the counter") and the continuation return_home in the same episode. The sim is paused between LLM calls — physics only advances inside env.step(), which only the motion tools drive. This measures capability, not API latency (the paper's protocol). At 50 Hz control (sim dt 0.005 s × decimation 4), a command of duration_s maps to N = 50 × duration_s control steps.

3.1 Turn lifecycle (pseudocode)

def run_stage(stage, state, sim, provider, tools):
    while True:
        # 1. Assemble the request — sim is PAUSED here
        msgs = [state.first_turn] + last_k_turns(state.transcript[1:], K=10)  # [1:]: no duplicate
        #   first turn while it is still inside the K window (early turns would
        #   otherwise pay the spawn image's token cost twice)
        mem  = render_memory_block(state.memory, state.counters,  # re-injected EVERY turn
                                   state.integrator.xy, sim.compass_deg())  # live, see 5.2
        req  = build_request(SYSTEM_PROMPT, mem, msgs, tools)     # images older than K dropped

        # 2. Model call (deterministic decoding where supported; retry 429/5xx w/ backoff)
        turn = provider.send(req)
        state.turns += 1
        log_usage(turn.usage)                                     # token + cost accounting

        # 3. Dispatch tool calls IN ORDER; motion tools advance physics via env.step()
        results = []
        for i, call in enumerate(turn.tool_calls):
            if call.name == "declare_done":
                # The declare_done turn is KEPT: append it with a tool_result for
                # EVERY call id in it (the echoed assistant turn must have its
                # tool_use blocks answered, sec 7.2). declare_done's own result
                # carries the stage outcome -- on stage 1, the return_home
                # objective (sec 3.3). Calls listed after declare_done are not
                # executed; they get a structured not_executed result.
                score = score_stage(stage, context.playback.true_xy())  # scored HERE, so a
                #   `move` bundled AHEAD of declare_done in the same turn counts
                results.append(stage_end_result(stage,          # return leg only on a
                    continue_to_return_home=score.success))     #   SUCCESS -- sec 3.3
                results += [not_executed(c.name) for c in turn.tool_calls[i+1:]]
                state.transcript.append(turn, results)
                return end_stage(stage, state, reason="declare_done", score=score)
            results.append(dispatch(call, context))               # bad call -> structured error
            if context.playback.fell:
                log_turn(...)                                     # doc 06 sec 4's record is
                return end_stage(stage, state, reason="fall")     #   STILL written; only the
                                                                  #   provider transcript entry
                                                                  #   is dropped, and it is moot
                                                                  #   (no further model calls).
                                                                  # A fall ends the TRIAL.
        if not turn.tool_calls:                                   # sec 8's derailment row: the
            results = [DERAILMENT_NUDGE]                          #   fixed nudge, then continue
        state.transcript.append(turn, results)                    # all results, one message

        # 4. Caps (checked after execution; capped stages scored as failures, never retried)
        if state.turns >= 40:            return end_stage(stage, state, reason="turn_cap")
        if state.policy_seconds >= 240:  return end_stage(stage, state, reason="motion_cap")

  1. Shipped signatures. T3.2 narrowed three of them and the loop uses the real ones: stage_end_result(stage, *, continue_to_return_home) (not (stage, state)), not_executed(tool_name: str) (not not_executed(call)), dispatch(call, context: ToolContext) (not (call, sim, state)), and context.playback.fell (not state.fell). Likewise sim.compass_deg() in phase 1 is tools.observed_compass_deg(context), which returns the latched heading after a fall — the live sensor reports the spawn pose Isaac teleported to (§4.1).
  2. A turn with no tool call had no branch. §8's refusal/derailment row requires the harness to append the fixed nudge and continue, but as literally written the loop would have appended an assistant turn with no tool_use and an empty user message — an API 400, i.e. §8's infra path, for a model failure §8 says must be scored. The branch is now explicit.
  3. The fall turn is still logged. §3.1 returns without state.transcript.append and justifies the drop ("no further model calls, so the dropped turn is moot") — but that is the provider transcript. Doc 06 §4 still requires turns[].execution / pose_trace for that turn, and T4.1's scorer raises without it. The two artifacts diverge here by design.
  4. declare_done is scored at its position in the call list, from playback.true_xy() — so a move bundled ahead of it in the same turn counts and the model is judged from where it actually ended up. The predicate is duck_embody/tasks/find_kitchen.py::score_stage, which T4.1's scorer also calls; its decision inputs (true pose, distance, radius, goal) go into the log so the scorer recomputes the verdict rather than trusting it.
  5. The return leg is conditional — see §3.3, resolved by T3.4. tasks.find_kitchen.runs_return_home() is asked once and its answer drives both the tool_result the model receives and whether the stage runs, so those two cannot disagree.
Two things the loop must NOT do, both pinned by tests/test_loop.py: catch anything around provider.send or dispatch (§8's infra path — a swallowed render error launders a broken GPU into a model failure), and fold the memory block into the system string. The system prompt plus the tool schema is the stable prefix doc 06 §8 counts on for prompt caching; a block that changes every turn would invalidate it on every single request, so the block rides in a trailing, non-persisted user message instead.

3.3 Stage transition: find_kitchen → return_home

When find_kitchen ends via declare_done and the distance test passes, the harness: (1) scores stage 1 from ground truth (the model never sees the numeric score or the distance; the only signal it gets is whether the return leg is offered — see the decision box below), (2) resets the per-stage counters (turns → 0, policy-seconds → 0), (3) keeps the memory object and the transcript window intact — the whole point is that the map built on the way out should pay off on the way back; the declare_done turn itself stays in the transcript, with every tool call it bundled (memory writes included) answered by a tool_result (§3.1) — and (4) delivers the new objective as the declare_done call's tool_result, in the same user message as the turn's other results (satisfying the tool_use/tool_result pairing, §7.2): "New objective: return to your starting position and call declare_done when you are there." If stage 1 ends by cap, by fall, or by a declare_done outside the target radius, return_home is not attempted and is scored as a failure.

RESOLVED BY T3.4 — does return_home run after a stage-1 cap-out? No. Nor after a wrong-place declare_done: stage 2 runs iff stage 1 SUCCEEDED.

The literal open question was never actually contested — this section, doc 06 §3.2 and doc 01 §8 all already said no to a cap-out. Reading the three together to settle it surfaced a contradiction they did have, on a case far more likely than a cap-out: §3.1/§3.3/§4.4 here triggered stage 2 on "stage 1 ended via declare_done" with the score not consulted, while doc 01 §8 and doc 06 §3.2 triggered it on "stage 1 succeeded". They differ exactly when the model declares done outside the 0.35 m target region — which both of those docs separately call a failure. Doc 05 is the one amended; docs 01 and 06 needed no change.

The decisive reason is measured. Under "any declare_done", a wrong declare that happens to land inside the 0.5 m home disc scores return_home a success with zero motion, and one such trial is 25 percentage points of a success rate at N=4 (doc 06 §6's honesty clause). Under "succeeded" that is geometrically impossible: stage 2 always begins within 0.35 m of the counter, whose worst-case distance to a spawn point is 1.574 m (seed 104) against a 0.5 m return radius — every seed clears it, and the guarantee is already load-bearing in tests/test_layout.py (spawn > 3 × 0.35 m from target, doc 06 §9.2). The alternative has no floor and would need an unprincipled extra guard no doc specifies. Supporting reasons: comparability (every stage 2 starts from the same disc, so d_initial, the SPL oracle length and time-to-home are homogeneous across trials and models); doc 06 §3.1's own statement of what stage 2 is for ("the model must navigate back using only what it wrote down" — a return leg from a spot the model never navigated to is not that test); and cost, on a stage AGENTS.md §8 lists first in the cut order. measured: tests/test_loop.py::TestStageTwoGate recomputes the 1.574 m worst case from apartment_layout.LAYOUT and fails if it ever stops clearing the return radius

What this costs, recorded rather than buried. declare_done's tool_result now differs by outcome, so the model can infer pass/fail at the transition — which is why item (1) above is reworded. Mitigations: the failure branch's text is outcome-neutral and byte-identical to stage 2's trial-over text ("The trial is over; no further tool calls will be executed."), so it says the run ended, never that the model was wrong; and on that branch the trial is over, so the model is never sent anything again and the only thing that reads the result is the log. The residual blast radius is the post-episode QA exchange (doc 06 §5.9), which runs after the episode either way and is scored against ground truth. Recorded in the write-up.

The rule now lives in a config — configs/benchmark.yaml: protocol.stage2_requires_stage1_success — so it sits inside doc 06 §2/§7's hashed fairness contract. It previously lived in no config at all. Implementation: duck_embody/tasks/find_kitchen.py::runs_return_home, asked once per trial and used for both the tool_result and the branch.

RESOLVED BY T3.4 — how stage-2 time is accounted (doc 06 §12's second half of the same question). The budget resets at the boundary and the caps do not change, so the first stage-2 request renders Budget: turns 0/40, policy-seconds 0.0/240. That is what item (2) above already said and what Counters / ToolContext.reset_for_stage() already implemented; it is stated outright here because it was only ever implied. A cumulative line would show turns 31/40 on the model's first return-home request — an immediate false cap — and doc 06 §5.4 (time from stage start), §5.5 (per-stage turns used) and §5.8 (drift series per stage) all require the per-stage reading anyway. There is no presentation discontinuity because §5.2's block is regenerated fresh into every request and never stored in the transcript, so the model never sees a stale pre-reset budget line. An unrun stage 2 reports outcome not_run with turns 0 and policy-seconds 0.0.
Multiple tool calls per turn are allowed and executed in listed order. This lets a model bundle memory writes (update_room, mark_exit, update_plan) with one motion command in a single turn — important because the 40-turn cap counts model calls, not tool calls. All results return in one message, per Anthropic's parallel-tool-use guidance — not an API-rejected shape (consecutive same-role messages are merged server-side), but splitting results across messages silently trains the model to stop making parallel calls (§7.2). Motion tools inside one turn execute sequentially and each advances physics; policy-seconds accumulate across them.

PINNED BY T3.2's review pass: a fall has already teleported the robot, so the perception tools are the ONLY ones still answered. Isaac Lab auto-resets a terminated env inside env.step() and returns the post-reset observation, so every live sensor read after a fall describes the spawn point — policy_wrapper.execute guards its own true_pose against exactly this, and tools.py inherited none of that care. Two consequences, both fixed in T3.2's review commit: compass_deg() is latched at the fall rather than re-read (see §4.2), and the three motion tools refuse to run at all once playback.fell is set (§8's stage_ended row). The perception and memory tools stay answerable, because the pin above requires get_observation to report fell "however it is reached" and they step no physics. Residual, assigned to T3.4: a get_observation listed after the falling command in the same turn renders its frame from the respawn point. That is the only way to reach it, it is one frame at the end of a trial that is already lost, and the fix belongs in the loop — T3.4 must end the stage on status.fell.
PINNED BY T3.2: who owns the camera, and how a look_around frame becomes base64. SimSession owns no camera (nothing outside scripts/ constructs one), so tools.ToolContext takes an injected HeadCamera — which is also what makes the tool layer unit-testable without a kit process, as PLAN T3.2's "sim mocked" requirement demands. HeadCamera.look_around() returns raw numpy arrays and capture_jpeg/capture_b64 could not encode them: both re-capture_rgb() at the robot's own heading, so routing a panorama frame through them would silently encode a fifth, forward-facing frame and label it "view at compass 90°". T3.2 therefore adds module-level camera.encode_jpeg(rgb, quality) / encode_b64 (doc 04 §5.3, updated in the same commit) and capture_jpeg/capture_b64 now delegate to them, so there is exactly one encoder and one place enforcing the frozen 512×512.

PINNED BY T3.2 (AGENTS.md rule 5): the four things the table above left open, plus the model-facing key names. Each was reachable from a tool call and settled by no doc.
  1. move(distance_m ≤ 0) → invalid_args. The schema's domain is (0, 1.5], open at zero, but §4.2 stated a failure mode only for the upper bound, and policy_wrapper.move does max(0.0, min(distance_m, 1.5)) — a zero or negative argument becomes a no-op that still runs a chunk, burns a turn and explains nothing. There is also no honest clamp available: raising 0 to some positive distance invents a command the model did not give, and clamping −1 to +1 would drive the robot the opposite way from what a model that typed −1 meant. The hint routes it to send_velocity with a negative vx, which is what the escape hatch is for. The upper bound still clamps, per the table — and the clamp note is synthesised in tools.py, because the wrapper performs that clamp silently and adds nothing to clamp_notes.
  2. turn_to_heading outside [0, 360) → wrapped, with the wrap echoed. An angle modulo 360 has exactly one meaning, so wrapping is arithmetic rather than the intent-guessing §8 forbids; but wrap_deg would do it silently, and a model that asked for 725° and was sent to 5° could never notice its own arithmetic slipped. The echo follows mark_exit's 15° snap precedent (§5.1).
  3. duration_s ∈ [0.2, 3.0] clamps, and now exists in code. It was stated in §4's schema description and doc 02 §6.3 and implemented nowhere — execute() accepts any duration, so a duration_s: 60 would have spent a quarter of the 240 s stage budget in one blind command. It is tools.DURATION_RANGE_S, mirrored into configs/benchmark.yaml (locomotion.send_velocity_duration_s) with an agreement test, following the caps precedent. A sub-0.2 s request clamps up: that is what "clamped to [0.2, 3.0]" says, the echo makes it visible, and rejecting would spend the model's scarcest budget (a turn) on a command the hull can perfectly well run.
  4. send_velocity's distance_moved_m = hypot(vx, vy) × policy_seconds (commanded, clamped values). Doc 04 §6.2 defines the field as "dead-reckoned distance actually covered by the most recent motion command", but ExecResult.dead_reckoned_distance_m is set by move only and is 0.0 on every other result — reporting it raw would tell the model it had not moved. Speed × time is the arc length of the commanded motion, and it is the same rule move reports.

Model-facing key names, which §4's prose "Returns" columns named only in part. Frozen here so a later refactor cannot change what the model reads without a doc diff: every motion result carries doc 04 §6's compass_deg / position_estimate / status block plus policy_seconds; turn_to_heading adds requested_heading_deg, heading_error_deg and timed_out; move adds requested_distance_m; send_velocity adds executed {vx, vy, wz, duration_s} (the clamped echo). Any clamp, wrap or snap appears in a single notes list — absent when nothing was changed, so the key stays a signal rather than decoration. policy_seconds is the macro's merged figure and is never ExecResult.duration_s, which _merge() leaves stale at 0.2 s on every macro result. The key set is now asserted per tool for all 12 in tests/test_tools.py, which is also the only net that catches a leak arriving under a new key name.

PINNED BY T3.2's review pass: four more things reachable from a tool call and settled by no doc.
  1. The requested_* keys carry the model's RAW argument, not the clamped or wrapped one. They first shipped carrying the adjusted value, so move(distance_m=5.0) answered requested_distance_m: 1.5 and turn_to_heading(725) answered requested_heading_deg: 5.0 — a key named "requested" reporting something the model never requested, recoverable only by cross-referencing notes, the one key this section deliberately makes absent when nothing changed. The repo's own precedent is the other way: §5.1's mark_exit ack "echoes the raw value, so the snap is visible rather than silent". What actually ran stays readable in two places that are always present — the clamp/wrap note names both numbers whenever they differ, and status.distance_moved_m / compass_deg report the outcome on every call. send_velocity is unchanged: its executed block is defined above as the clamped command echo, and the seconds that actually elapsed are policy_seconds.
  2. move serves distance in 0.04 m increments and rounds UP. policy_wrapper.move servos in whole 0.2 s chunks worth MOVE_SPEED_MPS × MACRO_CHUNK_S = 0.04 m each and breaks on travelled ≥ distance / k, so a move is never short of the request and may exceed it by up to 0.04 m: move(1.5) covers 1.52 m — past §4's own (0, 1.5] domain — and move(0.05) covers 0.08 m. Documented rather than "fixed": shortening the final chunk changes a doc 02 §6.2 macro that T2.4's physics pass validated, and echoing it as a clamp note would fire on essentially every call, turning notes from a signal into decoration. The model is told the real figure in status.distance_moved_m after every single move, which is the number it needs for final positioning against doc 06 §5.3's 0.35 m radius. Pinned by test so the granularity cannot change silently.
  3. After a fall, compass_deg is the heading latched BEFORE the command, not a live read. See §4.1's teleport pin for why the live sensor is the spawn point. ExecResult.true_pose[2] is deliberately not used: it is scoring-only (doc 06 §4) and may not cross into a payload. The latched value is written into the breadcrumb too — the trail is permanent and re-injected every turn (§5.2), so a spawn heading recorded there is unrecoverable.
  4. The scoring-side channel: ToolOutcome.execution. dispatch is the only code in the harness that ever sees an ExecResult, so dropping it is exactly as silent as leaking it and strictly more expensive: doc 06 §4 requires turns[].execution.pose_trace in every trial JSON, §5.3 pins the SPL path integral p to those 5 Hz sub-turn samples (and warns that chord-summing the once-per-turn true_pose entries instead "would under-measure any within-turn curved motion … shrinking p and inflating SPL"), and PLAN T4.1's scorer is specified to raise on a missing pose_trace. Every motion tool therefore returns a ToolOutcome.execution dict (pose_trace, sampled_xy, true_pose, true_displacement_m, policy_seconds_used, distance_moved_m, bumped, fell, stop_reason, counted_as_bump) for T3.4 to log; it is None for every tool that steps no physics. It is an attribute rather than a payload key precisely so to_block() — the only path to a provider — cannot carry it by accident, and a test asserts the two never meet. The key-name freeze above is model-facing only and does not cover it.
The dead-reckoning feed for move — PLAN T3.2 (b) was WRONG as written, and is corrected in T3.2's commit. (b) said to feed PositionIntegrator.integrate() the ExecResult.policy_seconds actually run. That is right for send_velocity and wrong for move: PolicyPlayback.move() appends a trailing 0.2 s zero-command settle chunk and merges it into policy_seconds, while travelled (→ dead_reckoned_distance_m) accumulates driving chunks only. Integrating 0.2 m/s over the merged figure fabricates 0.2 × 0.2 = 0.04 m of forward motion per move call — up to 1.6 m over a 40-turn stage, injected straight into doc 06 §5.8's drift metric: precisely the failure (b) exists to prevent, inverted. The correct feed is dead_reckoned_distance_m / MOVE_SPEED_MPS, which recovers the driving seconds exactly (every chunk is a whole number of 50 Hz steps, so duration_to_steps round-trips it), integrated along the heading move holds. Merged policy_seconds is what charges the 240 s cap; dead_reckoned_distance_m is what feeds the integrator. They are different numbers by design and conflating them in either direction fails silently.

turn_to_heading has the same trailing chunk but commands vx = vy = 0, so it feeds the integrator nothing at all: a rotation in place displaces the estimate by exactly zero, and real slip during the turn is drift the integrator is supposed not to see (§5.1).

send_velocity integrates the arc, not a chord. It is the only tool that can translate and rotate at once, and doc 02 §6.3's pseudocode integrates such a command in one call at one heading. For send_velocity(0.222, 0, 0.5, 3.0) — 86° of sweep over 0.67 m — that misplaces the estimate by ~0.45 m, against a 0.35 m find_kitchen success radius. That error is the harness's arithmetic, not the robot's slip, so T3.2 adds PositionIntegrator.integrate_arc(), which advances the heading by degrees(wz) × CONTROL_DT per control step from the commanded wz — no sensor read, and identical to integrate() step for step when wz = 0. Doc 02 §6.3 records the deviation.

5.1 Data structures (duck_embody/agent/memory.py)

                                # never model-writable (T3.1 review)

class PositionIntegrator:
    """Dead reckoning: per 50 Hz control step, rotate the COMMANDED body-frame
    velocity (vx, vy) into the world frame using the compass heading and
    accumulate x += v_world_x * dt, y += v_world_y * dt.  Commanded != actual
    (slip, gait dynamics, bumps), so the estimate drifts honestly.
    correct_position(x, y) overwrites (x, y); heading is never reset."""

Dead reckoning means estimating position by integrating velocity over time from a known start — the naval technique. Ours integrates the commanded velocity (what the LLM asked for), not measured velocity, because the deployed observation stack has no linear-velocity sensor source: parent .claude/rules/rl-training.md — v4_robust actor obs is 59-dim with NO base_lin_vel; BNO055 cannot measure it. The breadcrumb trail is the harness's only autonomous write into memory, and it is pure sensor-realistic state (declared exception (b) in §1) — it records where the integrator thinks the robot has been, never where it truly is.

Implementation deviations recorded by T3.1 (AGENTS.md §3 rule 5 — these amend the listing above rather than living only in the code):
  • Memory.room_sequence added. §5.2's worked example renders Trajectory: living_room -> hallway, but the dataclass above had no temporal field at all, and §1 forbids the harness deriving room identity itself — so the sequence must come from the model's own set_current_room assertions, and it must be stored somewhere. Consecutive repeats are collapsed (re-confirming the room you are already in would otherwise render hallway -> hallway -> hallway); a genuine revisit a→b→a keeps all three, because that is the trajectory. Not reset at the stage transition — §3.3 keeps the memory object intact.
  • Exit.direction_deg stores the snapped direction, not the raw assertion. §4.3 keys exits on the 15° grid; storing the raw value would render exit at 272 deg for a record that a later mark_exit(268) silently overwrites, leaving the model unable to predict which of its own exits it was addressing. The ack echoes the raw value, so the snap is visible rather than silent — the way clamp_command echoes clamps. Snapping is half-up, not Python's banker's round(), which would snap 7.5° down to 0° but 22.5° up to 30°.
  • PositionIntegrator interface pinned: __init__(x, y) at the seed's spawn coordinates; attributes x/y plus an xy property; step(vx, vy, heading_deg, dt=CONTROL_DT) for one control step; integrate(vx, vy, heading_deg, duration_s), whose step count comes from the sim's own duration_to_steps so the estimate cannot disagree with the commanded motion for reasons unrelated to drift; and correct(x, y) -> old_xy. It holds no heading of its own — the caller passes the compass reading valid for each interval, which is what "heading is never reset" means in practice. No k appears anywhere in it (PLAN T1.3's pinned policy). The same commit removed a * k from policy_wrapper.move()'s dead_reckoned_distance_m, which was moving the number the model is told 0.4 % toward the true displacement and so shrinking the drift doc 06 §5.8 exists to measure.
  • Correction.old_xy/new_xy are typed tuple[float, float], and every dataclass field takes a default so Memory() is the turn-0 state (plan starts ""). Correction.turn is the stage-local turn index — §3.3 resets the counters while keeping this object, so two corrections in one trial can share a value. CORRECTED by T3.1's review pass: an earlier revision of this bullet claimed "list order disambiguates them". It does not — list order gives the sequence, not the stage boundary, so a stage-2 correction on turn 12 was byte-identical to a stage-1 one and doc 06 §5.8's per-stage reporting would have been unrecoverable after the batch. Memory.stage and Correction.stage (above) fix it: the loop sets memory.stage once at the §3.3 transition and correct_position stamps it.
  • The memory tools return structured dicts, never exceptions: an ack {ok: true, detail, …} or the §8 error shape {error: "invalid_args", detail, hint}. Room lookups are exact — no case folding, no synonym table. The synonym table in prompts.py is a scoring artifact and applying it here would be the harness guessing the model's intent (§8: "the harness never guesses intent") and quietly repairing its graph (§1).
  • Argument validation lives HERE, and is type-only (added by T3.1's review pass, which found every memory tool raising an uncaught TypeError/ValueError on a wrong-typed argument — mark_exit("hallway", "270", "unexplored") died inside wrap_deg's "270" % 360.0, and correct_position wrote x before coercing y, leaving the estimate half re-anchored with nothing in the correction log). That contradicted the bullet above, and it matters beyond tidiness: §8 classifies an escaping harness exception as an infra fault and reruns the trial whole, so a malformed argument would have bought the model a free retry — the selection bias §8 exists to prevent — while §8's own first row says args that fail validation come back as invalid_args and the turn still counts. The rules, which PLAN T3.2 relies on when it calls tools.py "the wire, not a second implementation":
    • String fields (room/name, description, status, reason, plan text) must be strings — required, never coerced: str(None) would create a room literally named None.
    • Number fields (direction_deg, x, y) go through float(), so the numeric strings models emit for number-typed fields ("270") parse — that is parsing, not intent-guessing, since the result is exactly what the schema asked for. bool is excluded; non-finite values are rejected (json.loads accepts the NaN/ Infinity literals, and inf % 360 is nan).
    • correct_position validates BOTH coordinates before writing EITHER.
    • A room name that is empty or all-whitespace is rejected: it cannot be addressed by a later set_current_room and renders as Place 1: -- … with a blank Trajectory: entry. This is the ONLY rule applied to a name — no trimming, no case folding.
    • update_plan rejects a plan over 2000 characters (memory.PLAN_MAX_CHARS) — rejected rather than truncated, because §4.3 pins the plan as verbatim and a silent prefix would show the model a plan it never wrote. Rationale in §5.2's size note.
    None of this inspects meaning: a wildly wrong but finite anchor, a forward-referencing leads_to:, a duplicate room under a new name all still go through untouched (§1, §4.3).
EXTENDED BY T3.2 (AGENTS.md rule 5): the same rules now cover the MOTION arguments, and the two checks that could never live here.

(a) Scope. The rules above were written for the memory tools, so nothing covered heading_deg, distance_m or vx/vy/wz/duration_s — and §8's first row obliges invalid_args for those too. Concretely: clamp_command("0.2", 0, 0) raises TypeError (str < float), which §8 would misclassify as infra and rerun the trial whole; and clamp_command(nan, 0, 0) silently returns nan — every min/max comparison against NaN is False — which then poisons the command buffer and the position estimate, unrecoverably and without a traceback. memory._text_error / memory._number are therefore now public as memory.text_error / memory.number_arg and tools.py calls them directly. One implementation, deliberately: two copies would eventually disagree about whether "270" is a number, and the model would see one tool parse what another rejected.

(b) Arity and surplus arguments live in tools.py, because they structurally cannot live here. The memory tools are ordinary Python methods, so a call missing a required key — or carrying an extra one — dies on the ** splat with a TypeError before their own validation runs, again buying the free trial rerun. tools.dispatch checks the schema's required/properties before any handler is entered. Surplus keys are rejected, not dropped: silently ignoring the second argument of turn_to_heading(heading_deg=90, distance_m=1.0) is the harness guessing it was surplus rather than a conflation of two tools (§8: "the harness never guesses intent"), and the model would never learn that half of what it asked for was discarded. This is also why §4's schemas carry no additionalProperties: false: enforcement here returns invalid_args and the turn counts, whereas provider-side rejection would arrive as an API error and the turn would not.

5.2 The rendered memory block — MapGPT grammar, concrete example

Every turn, the harness renders Memory into one text block and injects it — so it survives context truncation. Rendering follows the MapGPT map-as-prompt grammar: numbered "Place" nodes, explicit adjacency lines, a one-line trajectory, and a separate unexplored-exits list (their finding: models plan better over an explicit textual map than over raw history). Example, mid-trial:

== YOUR MAP (authored by you; rendered verbatim by the harness) ==
Place 1: living_room -- sofa along the west wall, armchair opposite, blue rug in center
  landmarks: coffee table; armchair by the south wall
Place 2: hallway -- narrow, wooden floor, doorways along the south side
Connections: living_room <-> hallway
Trajectory: living_room -> hallway
Unexplored exits:
  - hallway: exit at 0 deg (unexplored)
  - hallway: exit at 270 deg (unexplored)
  - living_room: exit at 0 deg (unexplored)

== STATE (sensor-derived; the declared exceptions) ==
Position estimate: x=0.90, y=2.75  (dead-reckoned from commanded velocity; drifts)
Compass heading: 88 deg
Current room (your assertion): hallway
Breadcrumbs (last 5): (0.50,0.50,90) (0.53,1.11,88) (0.85,1.95,68) (0.88,2.56,87) (0.90,2.75,88)
Budget: turns 12/40, policy-seconds 63.4/240

== YOUR PLAN (update_plan to change; carried forward otherwise) ==
Kitchen unlikely behind me. Follow the hallway east (exit at 0 deg) and check the
next doorway at 270 deg; if tiled floor or counters appear, switch to contextual
search for the counter.

Heading convention throughout (compass, breadcrumbs, exit directions): degrees counter-clockwise from +x, so 0° = east and 90° = north — the layout convention of Doc 03 §3. The dead-reckoning integrator is initialized at the seed's spawn coordinates (the "known start" of dead reckoning), so estimates and the scorer's true poses share one world frame — the example above is seed 101, spawn (0.5, 0.5) heading 90°.

Why re-inject every turn instead of trusting the transcript? The Anthropic paper observed models leaning on the recent past and forgetting older discoveries. Context policy: system prompt + first turn + last K=10 turns are kept; older turns — and any images inside them, including the first turn's image once it ages past K — are dropped. The memory block is the one artifact exempt from truncation: it is regenerated fresh into every request, so a fact asserted on turn 3 is still in front of the model on turn 38, at constant token cost.
PINNED BY T3.4: exactly what "first turn" is, and where the block rides.
  • state.first_turn is state.transcript[0] — the first (assistant turn + its tool_result message) exchange, whatever it contains. §3.1's transcript[1:] slice is what proves it. Nothing precedes it: the model's turn 1 is unprompted after the system prompt, which already carries the stage-1 objective, plus the per-turn memory block. For a model that opens with get_observation (all of them are expected to) that first entry is the one carrying the spawn-point image §12 discusses. The effective window is therefore 1 + min(K, len−1) entries — never K+1 with one of them repeated.
  • It is TRIAL-scoped, not stage-scoped. §3.3 item (3) keeps the transcript window intact across the boundary, so stage 2 still has stage 1's first turn pinned. Stage-scoping it would silently change what the pin means halfway through a trial.
  • The memory block is a trailing, non-persisted user message, not part of the system string and never appended to the transcript. Folding it into system would destroy the stable prefix doc 06 §8 counts on for prompt caching (the block changes every turn); storing it in the transcript would show the model a stale budget line and a stale position beside the live ones. Consecutive user messages are merged server-side, which §3.3 already sanctions.
Rendering rules pinned by T3.1 (the example above is mid-trial and rich, so it leaves most of these open; the golden test in tests/test_memory.py extracts the block above from this file and asserts render_memory_block reproduces it byte for byte, so the doc and the renderer cannot drift):
  • Signature. §3.1's pseudocode calls render_memory_block(state.memory, state.counters); the implementation is render_memory_block(memory, counters, position_estimate, compass_deg). The two live sensor readings are passed explicitly rather than read off the last breadcrumb because correct_position re-anchors the integrator without appending a crumb (§5.1: crumbs follow motion commands), and a block that rendered the pre-correction position immediately after the model corrected it would be showing the model a number it had just overwritten.
  • Ordering. Place N follows rooms insertion order, 1-based, and an update_room upsert keeps a room's slot, so its number is stable for the whole episode. Connections: renders one line per undirected edge, in exit-creation order, source room on the left; reciprocal assertions (a→b and b→a) collapse to one line. (This clause said "in the order the model first asserted it" until T3.1's review pass, which found the implementation ordering by the position of the source exit in Memory.exits — where that exit was first mark_exit'd, not where its status later became leads_to:. Upgrading a long-standing unexplored frontier therefore renders its edge above an edge asserted earlier on a newer exit. Amended rather than fixed in code, per AGENTS.md rule 5: both rules are stable and deterministic, and the model sees only a fixed line order either way. The discriminating case is now tested — the example above, where no exit is ever upgraded, cannot tell them apart.) Unexplored exits sorts by room name, then ascending direction — the only rule that reproduces the example above, where living_room is Place 1 yet renders last.
  • Which exits go where. leads_to: exits render as Connections: and are excluded from the unexplored list (doc 06 §5.7: an unexplored exit is not an adjacency assertion). An edge whose target room the model never created still renders — dropping it would be the harness repairing the model's graph (§1).
  • Empty collections. The example pins exactly one case: a room with no landmarks omits its landmarks: line. The rest is T3.1's: Connections:, Trajectory: and the whole Unexplored exits: block are omitted when empty; the three == … == headers and the five STATE lines always render (a sixth, Re-anchored:, is conditional — see below); and every fixed line with nothing to show renders the single token (none yet) — one signal everywhere rather than bespoke wording per slot, so the block's shape does not change under the model between turn 1 and turn 40.
  • Numbers. Positions 2 decimals always (x=0.90 keeps its trailing zero), with -0.00 folded to 0.00. Compass, breadcrumb and exit headings are integers, half-up and wrapped to [0, 360) — 359.7 renders 0, never 360; half-up rather than Python's banker's round(), which would render 88.5 as 88 and 89.5 as 90 for reasons the model cannot see. Policy-seconds 1 decimal; turn counts and both caps bare integers. The breadcrumb window is fixed at 5 and the label stays (last 5) even when fewer exist: it names the window, not the count.
  • Conditional STATE line: Re-anchored: (added by T3.1's review pass). After correct_position, the breadcrumb list legitimately mixes coordinate frames — crumbs are the honest record and are never rewritten — so the series contains a jump no motion command explains (1.30 m backwards inside a 0.5 m move, in the reviewed case), while Position estimate: shows the corrected value. The tool_result that explained it is dropped once its turn ages past the K=10 window, after which the discontinuity is indistinguishable from a bad integration: noise in the exact metric (doc 06 §5.8) that correct_position exists to serve. The block therefore carries one derived line after Breadcrumbs, rendered only when at least one correction exists (so the example above is unchanged): Re-anchored: N time(s) (latest moved the estimate X.XX m; breadcrumbs before it are in the old frame). It carries no new information across the §1 boundary — both numbers are the model's own correct_position calls, and the magnitude is what that call's ack already returned as delta_m; the line only makes them survive the context window, which is what the whole block is for. No turn index: Correction.turn is stage-local (§3.3), so a stage-1 index shown during stage 2 would read in the wrong frame, and the crumbs carry no turn indices to align it with anyway.
  • Model-authored text is flattened to one line. Every model-authored string except the plan has its line breaks replaced by spaces at render time. Without it, a landmark containing "\n== STATE …\nPosition estimate: x=9.99, y=9.99 (dead-reckoned…)" renders a complete, correctly-formatted counterfeit STATE header and position line ABOVE the real one — two contradictory estimates in front of the model, in the QA prompt (which embeds the block verbatim), and in any post-hoc parser. Formatting only: nothing is dropped, no other character changes, and what is stored is untouched (§1).
  • Size. The block's cost is constant in the length of the episode — it does not grow with the transcript — but not constant absolutely: it grows with what the model writes into it. Only the plan is bounded (§4.3's 2000-character limit); rooms, landmarks and exits are deliberately unbounded, because refusing to record an observation the model made would be the harness editing the model's map (§1). The plan is the field worth capping because it is free text with no natural end and is re-injected into every turn of both stages plus the QA exchange.
  • Verbatim quirks that are not typos. Two spaces before (dead-reckoned; the separator is -- (two ASCII hyphens), <-> and -> are ASCII; degrees are the bare lowercase word deg; breadcrumb tuples have no space after their commas. The plan is stored and rendered verbatim, never re-wrapped (§4.3).

5.3 correct_position — cognitive loop closure

Loop closure in SLAM: when the robot recognizes a previously-visited place, the system corrects the accumulated pose drift. Here the recognition and the correction are both the model's job: it sees (say) the blue rug it described on turn 2, reasons "this is living_room, which I mapped around my (0.5, 0.5) start, so my estimate x=1.9 is drifted," and calls correct_position(0.6, 0.6, "recognized blue rug in living_room"). The harness obeys unconditionally and logs (turn, old_xy, new_xy, reason). The log serves two metrics: the dead-reckoning drift metric (|estimate − true| at goal, computed post-hoc against ground truth) and a qualitative audit of whether corrections helped or hurt — mis-anchored corrections are a predicted failure mode (§10).

6. Prompt design

One system prompt, frozen before the batch, identical for all three models — no per-model tuning source: AGENTS.md §3 rule 4. Outline (duck_embody/agent/prompts.py):

  1. Embodiment & physics. You are a 42 cm bipedal robot; camera at ~0.36 m, 90° HFOV — furniture looks large; doorways are ~0.35 m wide vs your ~0.16 m body, so center yourself before passing. Walking is slow (max 0.222 m/s forward); turning in place then driving beats sideways motion. A fall ends the trial — prefer short moves near obstacles.
  2. Tool documentation. The §4 schema descriptions, plus worked usage notes (e.g. "bundle memory writes with your motion command — turns are your scarcest budget").
  3. Navigation doctrine — a CogNav-style state machine. Operate in three explicit modes and name your current mode in your plan: broad search (sweep unexplored exits to grow the map), contextual search (kitchen-correlated evidence seen — tile, counters, appliances — bias exploration toward it), verify (believe you're at the counter: confirm with an observation before declare_done).
  4. Frontier scoring. A frontier is the boundary between explored and unexplored space — here, the unexplored-exits list. Each turn, briefly rate each unexplored exit for kitchen-likelihood from visual evidence and pick deliberately, rather than defaulting to the nearest.
  5. Plan carry-forward. Your plan is re-shown every turn; either act consistently with it or call update_plan — silent divergence is the failure pattern to avoid (MapGPT's carry-forward result).
  6. Honesty rules. Record only what you observed: never invent a room you haven't entered; mark uncertain exits unexplored rather than guessing leads_to; when lost, say so in the plan and navigate to a mapped landmark to re-anchor.
Deviation recorded by T3.1's review pass (AGENTS.md rule 5): where §4's schema descriptions actually reach the model. Item 2 above says the prompt carries "the §4 schema descriptions, plus worked usage notes". The implemented prompt carries the usage notes plus a prose paraphrase, and says so ("The full JSON schemas come attached to every request; these are the notes that are not in them") — the descriptions themselves reach the model through the API's tools parameter, which is where a tool-using model reads them, rather than being duplicated in the system prompt where the two copies could drift. The consequence, which T3.2 must honour: §4's numeric bounds — the send_velocity hull (vx ∈ (−0.148, 0.222), vy ± 0.111, wz ± 0.5, duration ∈ [0.2, 3.0] s) and turn_to_heading's [0, 360) domain — are stated in no model-facing text except those schema descriptions. tools.py must therefore use §4's description strings verbatim, and tests/test_tools.py must assert it (PLAN T3.2), or the frozen prompt would be silently thinner than this section specifies and the whole batch would be frozen that way. The prompt itself still states the operationally load-bearing part in prose: max 0.222 m/s forward, 1.5 m per move, and that every command is clamped to the trained envelope with the clamp echoed back.

    9. Prior-art anchoring

    Four systems anchor this design. MapGPT (Chen et al., ACL 2024; github.com/chen-judge/MapGPT) showed that rendering a topological map into the prompt — numbered place nodes, explicit adjacency, and an agent-updated plan carried across turns — beats raw history for vision-language navigation; we adopt its map grammar (§5.2) and plan carry-forward (§6.5) wholesale, but where MapGPT's map comes from an oracle discrete navigation graph, ours is authored entirely by the model. CogNav models object-goal navigation as an LLM-driven cognitive state machine (broad search → contextual search → candidate verification); we borrow it as prompt doctrine rather than code (§6.3). "Constructing coherent spatial memory in LLM agents through graph rectification" (the LLM-MapRepair line of work) demonstrates that LLM-built maps accumulate structural errors — duplicate nodes, wrong edges — that compound unless explicitly repaired; that finding motivates both correct_position and our decision to log every correction and graph edit for post-hoc audit rather than assuming the map is sound. Finally, Anthropic's embody experiments used an explore_report-style debrief to probe what the model actually retained; our post-episode layout QA (5 fixed questions answered from the model's own map, scored against the layout ground truth) is the direct descendant of that idea. sources: all four URLs fetched 2026-07-26, HTTP 200; arXiv titles verified from page <title> tags — see §11

    10. What we predict will fail (honest)

    • Revisit loops. The paper's headline negative result. Even with the map re-injected, a model that mis-asserts set_current_room once can walk a corridor twice believing it is new. Instrumented via: map-accuracy metric (room node precision/recall + adjacency edge accuracy vs the layout ground truth) and the breadcrumb trail, which makes physical loops visible even when the model's map denies them.
    • Hallucinated exits and phantom rooms. A 90° FOV frame of a shadowed corner can read as a doorway; mark_exit makes the hallucination durable, and frontier scoring (§6.4) then actively steers the robot at a wall. Instrumented via: map precision (invented rooms/edges lower it), bump counts clustered near hallucinated exits.
    • Drift mis-anchoring. The failure the graph-rectification paper predicts: the model "recognizes" the wrong landmark (two rooms share a similar rug) and calls correct_position to a wrong anchor — a correction that increases error and can corrupt subsequent mapping. Instrumented via: the correction log cross-referenced post-hoc with true pose at each correction turn (did |error| shrink or grow?), reported alongside the goal-time drift metric.
    • Doorway attrition. Not a memory failure but a compounding tax: 0.35 m doorways vs a 0.16 m body with dead-reckoned lateral error means repeated bumps; each auto-stop costs a turn to recover. Instrumented via: bump counts per trial and time-to-kitchen.

    All four are report material either way: the point of the benchmark is to measure exactly these behaviors across models, not to engineer them away.
