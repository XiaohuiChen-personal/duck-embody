Who should read this / what you'll learn. This document is the low-level design of the agent harness: the loop that lets a large language model (LLM — a text-and-image model such as Claude, called over an API) drive a simulated 42 cm bipedal robot through an unknown apartment using tool calls (structured function invocations the model emits instead of prose). It assumes no robotics or Isaac Sim background: every term of art — SLAM, dead reckoning, loop closure, frontier — is defined on first use. After reading you will know the exact turn lifecycle, the full tool schema, the memory data structures and how they render into the prompt, the provider adapters for the Anthropic and OpenAI APIs, and the error-handling and scoring boundaries. Code homes: duck_embody/agent/loop.py, tools.py, memory.py, prompts.py (currently docstring skeletons).

1. The core question: can an LLM be its own SLAM?

Anthropic's "How Claude Performs on Robotics Tasks" (Frontier Red Team, Jul 9 2026) reported a consistent negative finding: models navigating a quadruped from egocentric camera frames struggled with spatial memory — they re-explored visited areas, lost track of where they were, and leaned heavily on whatever was in the recent context window. Their harness (safety-research/embody) is unreleased source: 404 verified 2026-07-26, per AGENTS.md §1, and it deliberately provided little memory scaffolding. Duck Embody asks the follow-up question: if we give the model a well-designed externalized memory — but make the model itself author every fact in it — can it navigate an unknown apartment reliably? That is, we replace SLAM (defined below) with the model's own cognition plus a text notebook the harness faithfully re-displays.

Boundary principle (locked): "The harness stores and formats; the LLM perceives, estimates, and decides." No geometric fact enters memory unless the model asserted it from its own observations. WHY: the moment the harness starts injecting ground truth (real positions, real room labels, a geometry-built graph), the benchmark stops measuring the model's spatial cognition and starts measuring our scaffolding. Three declared, sensor-realistic exceptions mirror what a real robot's hardware provides for free: (a) compass heading (the BNO055 IMU on the physical duck gives absolute yaw), (b) dead-reckoned position integrated from commanded velocity (drifts honestly — commanded ≠ actual), and (c) closed-loop motion macros (turn_to_heading, move) that servo on those same two signals. Ground-truth position is never given to the model. source: AGENTS.md §3 rule 5

2. SLAM for newcomers — what we keep, replace, drop

SLAM (Simultaneous Localization And Mapping) is the classical robotics answer to "where am I, and what does this place look like?". A SLAM system provides three services: localization (a running estimate of the robot's pose — position + heading), mapping (a persistent model of the environment, e.g. an occupancy grid or landmark graph), and loop closure (recognizing "I've been here before" and snapping the accumulated pose error back to the earlier estimate). Under the hood it does heavy geometry: probabilistic filtering, bundle adjustment, uncertainty propagation over thousands of raw sensor readings.

We keep the three services but re-implement each as language, and drop the geometric machinery — a deliberate mirror of the "keyframe" philosophy in visual SLAM (keep a sparse set of informative snapshots, discard the raw stream):

SLAM serviceClassical implementationDuck Embody implementationKeep / replace / drop
LocalizationFilter fusing odometry + visionHarness integrates commanded velocity into an (x, y) estimate (dead reckoning — declared exception); compass gives headingKeep as breadcrumb position log
MappingOccupancy grid / feature mapModel-authored room / exit / landmark graph stored as text, rendered back every turnReplace: landmark memory as language
Loop closurePlace recognition + pose-graph optimizationModel re-recognizes a landmark and calls correct_position(x, y, reason) — cognitive loop closureReplace: cognition instead of optimization
Geometric optimizationBundle adjustment, pose-graph solvers—Drop
Uncertainty propagationCovariance tracking— (the model is told the estimate drifts; no numeric covariance)Drop
Raw sensor historyFull scan/image archive— (images older than the K=10-turn window are dropped; the map text is the durable record)Drop — keyframe philosophy

3. Episode loop design

One trial = one seed (101–104; seed selects spawn point + heading from the layout's spawn_points) × one model, run inside the single persistent Isaac Sim process source: AGENTS.md §3 rule 1 (one GPU job; kit startup is minutes). A trial contains up to two stages: find_kitchen ("Find the kitchen and walk to the counter") and the continuation return_home in the same episode. The sim is paused between LLM calls — physics only advances inside env.step(), which only the motion tools drive. This measures capability, not API latency (the paper's protocol). At 50 Hz control (sim dt 0.005 s × decimation 4), a command of duration_s maps to N = 50 × duration_s control steps.

3.1 Turn lifecycle (pseudocode)

# duck_embody/agent/loop.py (planned)
def run_stage(stage, state, sim, provider, tools):
    while True:
        # 1. Assemble the request — sim is PAUSED here
        msgs = [state.first_turn] + last_k_turns(state.transcript[1:], K=10)  # [1:]: no duplicate
        #   first turn while it is still inside the K window (early turns would
        #   otherwise pay the spawn image's token cost twice)
        mem  = render_memory_block(state.memory, state.counters)  # re-injected EVERY turn
        req  = build_request(SYSTEM_PROMPT, mem, msgs, tools)     # images older than K dropped

        # 2. Model call (deterministic decoding where supported; retry 429/5xx w/ backoff)
        turn = provider.send(req)
        state.turns += 1
        log_usage(turn.usage)                                     # token + cost accounting

        # 3. Dispatch tool calls IN ORDER; motion tools advance physics via env.step()
        results = []
        for i, call in enumerate(turn.tool_calls):
            if call.name == "declare_done":
                # The declare_done turn is KEPT: append it with a tool_result for
                # EVERY call id in it (the echoed assistant turn must have its
                # tool_use blocks answered, sec 7.2). declare_done's own result
                # carries the stage outcome -- on stage 1, the return_home
                # objective (sec 3.3). Calls listed after declare_done are not
                # executed; they get a structured not_executed result.
                results.append(stage_end_result(stage, state))
                results += [not_executed(c) for c in turn.tool_calls[i+1:]]
                state.transcript.append(turn, results)
                return end_stage(stage, state, reason="declare_done")
            results.append(dispatch(call, sim, state))            # bad call -> structured error
            if state.fell:
                return end_stage(stage, state, reason="fall")     # a fall ends the TRIAL
                                                                  # (no further model calls, so
                                                                  # the dropped turn is moot)
        state.transcript.append(turn, results)                    # all results, one message

        # 4. Caps (checked after execution; capped stages scored as failures, never retried)
        if state.turns >= 40:            return end_stage(stage, state, reason="turn_cap")
        if state.policy_seconds >= 240:  return end_stage(stage, state, reason="motion_cap")

3.3 Stage transition: find_kitchen → return_home

When find_kitchen ends via declare_done, the harness: (1) scores stage 1 from ground truth (the model never sees the score), (2) resets the per-stage counters (turns → 0, policy-seconds → 0), (3) keeps the memory object and the transcript window intact — the whole point is that the map built on the way out should pay off on the way back; the declare_done turn itself stays in the transcript, with every tool call it bundled (memory writes included) answered by a tool_result (§3.1) — and (4) delivers the new objective as the declare_done call's tool_result, in the same user message as the turn's other results (satisfying the tool_use/tool_result pairing, §7.2): "New objective: return to your starting position and call declare_done when you are there." If stage 1 ends by cap or fall, return_home is not attempted and is scored as a failure (see open questions for the cap case).

Multiple tool calls per turn are allowed and executed in listed order. This lets a model bundle memory writes (update_room, mark_exit, update_plan) with one motion command in a single turn — important because the 40-turn cap counts model calls, not tool calls. All results return in one message, per Anthropic's parallel-tool-use guidance — not an API-rejected shape (consecutive same-role messages are merged server-side), but splitting results across messages silently trains the model to stop making parallel calls (§7.2). Motion tools inside one turn execute sequentially and each advances physics; policy-seconds accumulate across them.

5. Memory system low-level design

5.1 Data structures (duck_embody/agent/memory.py)

@dataclass
class Room:                 # created only by update_room (model-asserted)
    name: str
    description: str
    landmarks: list[str]

@dataclass
class Exit:                 # created only by mark_exit
    room: str
    direction_deg: float    # absolute compass direction of the doorway
    status: str             # "unexplored" | "leads_to:<room>"

@dataclass
class Crumb:                # appended by the HARNESS after every motion command
    x: float; y: float; heading_deg: float      # from the integrator + compass

@dataclass
class Correction:           # appended on every correct_position call
    turn: int; old_xy: tuple; new_xy: tuple; reason: str

@dataclass
class Memory:
    rooms: dict[str, Room]
    exits: list[Exit]
    breadcrumbs: list[Crumb]
    current_room: str | None
    plan: str
    corrections: list[Correction]

class PositionIntegrator:
    """Dead reckoning: per 50 Hz control step, rotate the COMMANDED body-frame
    velocity (vx, vy) into the world frame using the compass heading and
    accumulate x += v_world_x * dt, y += v_world_y * dt.  Commanded != actual
    (slip, gait dynamics, bumps), so the estimate drifts honestly.
    correct_position(x, y) overwrites (x, y); heading is never reset."""

Dead reckoning means estimating position by integrating velocity over time from a known start — the naval technique. Ours integrates the commanded velocity (what the LLM asked for), not measured velocity, because the deployed observation stack has no linear-velocity sensor source: parent .claude/rules/rl-training.md — v4_robust actor obs is 59-dim with NO base_lin_vel; BNO055 cannot measure it. The breadcrumb trail is the harness's only autonomous write into memory, and it is pure sensor-realistic state (declared exception (b) in §1) — it records where the integrator thinks the robot has been, never where it truly is.

5.2 The rendered memory block — MapGPT grammar, concrete example

Every turn, the harness renders Memory into one text block and injects it — so it survives context truncation. Rendering follows the MapGPT map-as-prompt grammar: numbered "Place" nodes, explicit adjacency lines, a one-line trajectory, and a separate unexplored-exits list (their finding: models plan better over an explicit textual map than over raw history). Example, mid-trial:

== YOUR MAP (authored by you; rendered verbatim by the harness) ==
Place 1: living_room -- sofa along the west wall, armchair opposite, blue rug in center
  landmarks: coffee table; armchair by the south wall
Place 2: hallway -- narrow, wooden floor, doorways along the south side
Connections: living_room <-> hallway
Trajectory: living_room -> hallway
Unexplored exits:
  - hallway: exit at 0 deg (unexplored)
  - hallway: exit at 270 deg (unexplored)
  - living_room: exit at 0 deg (unexplored)

== STATE (sensor-derived; the declared exceptions) ==
Position estimate: x=0.90, y=2.75  (dead-reckoned from commanded velocity; drifts)
Compass heading: 88 deg
Current room (your assertion): hallway
Breadcrumbs (last 5): (0.50,0.50,90) (0.53,1.11,88) (0.85,1.95,68) (0.88,2.56,87) (0.90,2.75,88)
Budget: turns 12/40, policy-seconds 63.4/240

== YOUR PLAN (update_plan to change; carried forward otherwise) ==
Kitchen unlikely behind me. Follow the hallway east (exit at 0 deg) and check the
next doorway at 270 deg; if tiled floor or counters appear, switch to contextual
search for the counter.

Heading convention throughout (compass, breadcrumbs, exit directions): degrees counter-clockwise from +x, so 0° = east and 90° = north — the layout convention of Doc 03 §3. The dead-reckoning integrator is initialized at the seed's spawn coordinates (the "known start" of dead reckoning), so estimates and the scorer's true poses share one world frame — the example above is seed 101, spawn (0.5, 0.5) heading 90°.

Why re-inject every turn instead of trusting the transcript? The Anthropic paper observed models leaning on the recent past and forgetting older discoveries. Context policy: system prompt + first turn + last K=10 turns are kept; older turns — and any images inside them, including the first turn's image once it ages past K — are dropped. The memory block is the one artifact exempt from truncation: it is regenerated fresh into every request, so a fact asserted on turn 3 is still in front of the model on turn 38, at constant token cost.

5.3 correct_position — cognitive loop closure

Loop closure in SLAM: when the robot recognizes a previously-visited place, the system corrects the accumulated pose drift. Here the recognition and the correction are both the model's job: it sees (say) the blue rug it described on turn 2, reasons "this is living_room, which I mapped around my (0.5, 0.5) start, so my estimate x=1.9 is drifted," and calls correct_position(0.6, 0.6, "recognized blue rug in living_room"). The harness obeys unconditionally and logs (turn, old_xy, new_xy, reason). The log serves two metrics: the dead-reckoning drift metric (|estimate − true| at goal, computed post-hoc against ground truth) and a qualitative audit of whether corrections helped or hurt — mis-anchored corrections are a predicted failure mode (§10).

6. Prompt design

One system prompt, frozen before the batch, identical for all three models — no per-model tuning source: AGENTS.md §3 rule 4. Outline (duck_embody/agent/prompts.py):

  1. Embodiment & physics. You are a 42 cm bipedal robot; camera at ~0.36 m, 90° HFOV — furniture looks large; doorways are ~0.35 m wide vs your ~0.16 m body, so center yourself before passing. Walking is slow (max 0.222 m/s forward); turning in place then driving beats sideways motion. A fall ends the trial — prefer short moves near obstacles.
  2. Tool documentation. The §4 schema descriptions, plus worked usage notes (e.g. "bundle memory writes with your motion command — turns are your scarcest budget").
  3. Navigation doctrine — a CogNav-style state machine. Operate in three explicit modes and name your current mode in your plan: broad search (sweep unexplored exits to grow the map), contextual search (kitchen-correlated evidence seen — tile, counters, appliances — bias exploration toward it), verify (believe you're at the counter: confirm with an observation before declare_done).
  4. Frontier scoring. A frontier is the boundary between explored and unexplored space — here, the unexplored-exits list. Each turn, briefly rate each unexplored exit for kitchen-likelihood from visual evidence and pick deliberately, rather than defaulting to the nearest.
  5. Plan carry-forward. Your plan is re-shown every turn; either act consistently with it or call update_plan — silent divergence is the failure pattern to avoid (MapGPT's carry-forward result).
  6. Honesty rules. Record only what you observed: never invent a room you haven't entered; mark uncertain exits unexplored rather than guessing leads_to; when lost, say so in the plan and navigate to a mapped landmark to re-anchor.

7. Provider abstraction

7.1 Common interface

class Provider(Protocol):
    def send(self, system: str, messages: list[Msg], tools: list[ToolDef]) -> AssistantTurn: ...

@dataclass
class AssistantTurn:
    text: str                          # any prose the model wrote
    tool_calls: list[ToolCall]         # (id, name, args: dict) - args always a parsed dict
    usage: Usage                       # input/output tokens -> per-trial cost accounting
    raw: Any                           # provider-native turn, echoed back verbatim next turn
  • Deterministic decoding where the API supports it: the OpenAI adapter sends temperature=0 — pending a one-call probe that GPT 5.6 sol accepts it (OpenAI's recent reasoning-model families reject non-default temperature; unverifiable locally — §12); see the warning below for Anthropic.
  • max_tokens per model config (configs/models/*.yaml — one YAML per model: API params, context K, image size source: configs/models/README.md).
  • Retry: exponential backoff + jitter on HTTP 429 / 5xx / connection errors (both official SDKs do this natively; we set the retry count and log every retry). Exhaustion → infra-failed trial (§8).
  • Accounting: token counts from each response's usage object, multiplied by the price sheet in the model config; reported per trial.
"temperature 0" cannot be sent to the Anthropic models. The locked models claude-fable-5 and claude-opus-5 reject temperature / top_p / top_k with HTTP 400 (sampling parameters were removed on Opus 4.7+ and Fable 5), and Fable 5's extended thinking is always on. RESOLVED (T3.3, 2026-07-26): GPT 5.6 sol rejects it too — "Unsupported value: 'temperature' does not support 0 with this model. Only the default (1) value is supported." The conditional in this warning therefore resolves to its pessimistic branch: no locked model supports deterministic decoding. Every adapter omits sampling parameters entirely and we accept run-to-run variation from the models themselves. Trial-level reproducibility comes from fixed sim seeds, not decoding — and the results write-up must say so plainly rather than implying repeatable model behaviour. source: Anthropic model docs via claude-api skill reference (cached 2026-06-24); tool-use docs page HTTP 200 verified 2026-07-26

7.2 Anthropic adapter (Messages API tool use)

  • Tools pass through almost verbatim: {name, description, input_schema}.
  • The assistant turn contains tool_use content blocks: {id, name, input} with input already a parsed object.
  • Results go back as one user message whose content is a list of tool_result blocks — {type: "tool_result", tool_use_id, content: [...]} — one per call, all in the same message (splitting them degrades the model's parallel-call behavior). Camera frames ride inside a tool_result's content as base64 image blocks: {type: "image", source: {type: "base64", media_type: "image/jpeg", data: ...}} (frames are JPEG-encoded per Doc 04 §5.3).
  • The prior assistant turn's content is echoed back unchanged (including thinking blocks on Fable 5 — required for multi-turn continuity).
  • stop_reason is checked before reading content; a refusal falls into the derailment path of §8, not the infra path.

source: https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview.md (HTTP 200, 2026-07-26)

7.3 OpenAI adapter — Responses API, not chat completions

CORRECTED (T3.3, 2026-07-26) — chat completions does not work for this model. This section originally specified /v1/chat/completions. Measured against the live API: 
POST /v1/chat/completions -> 400
"Function tools with reasoning_effort are not supported for gpt-5.6-sol in
 /v1/chat/completions. To use function tools, use /v1/responses or set
 reasoning_effort to 'none'."
The error offers two escapes and only one is admissible. Setting reasoning_effort='none' would run the OpenAI contestant with reasoning disabled while both Anthropic contestants run with thinking on at the API default — not a wire-format detail but a handicap that would invalidate the very cross-lab comparison this third model exists to provide. The harness therefore uses /v1/responses, where function tools and reasoning coexist (verified: a probe returned a well-formed tool call alongside 19 reasoning tokens). This is exactly the failure T3.3 was pulled ahead of Phase 2 to catch; inside the frozen batch it would have cost four trials and a re-freeze.

Verified shapes (probed live, not assumed):

  • System prompt → the top-level instructions parameter, not a message.
  • Tools are flat: {type: "function", name, description, parameters}. This differs from chat completions, which nests them under function — confusing the two is a 400.
  • User content parts are input_text / input_image (not text / image_url), and the image is a bare data-URL string.
  • The model's turn returns a list of output items (reasoning, function_call, message) which are echoed back verbatim next turn. The reasoning items matter for multi-turn continuity the same way Anthropic's thinking blocks do.
  • A function_call carries call_id — what a result must reference, not id — and arguments as a JSON string that must be parsed, and can fail to parse (§8).
  • Results go back as their own items: {type: "function_call_output", call_id, output}, where output is a string.
  • max_output_tokens replaces max_tokens.

The asymmetry Doc 04 §6.1 flagged survives the API change: a tool result still cannot carry an image, so frames follow in an adjacent user message, labelled and attributed to the originating call_id.

Failure classDetectionPolicy
Malformed / unknown tool callUnknown name; args fail validation; unparseable arguments JSON (OpenAI)Return a structured error to the model as that call's tool result — {error: "unknown_tool" | "invalid_args", detail, hint}. The turn still counts against the 40-turn cap. The model is expected to self-correct; the harness never guesses intent.
Refusal / derailmentAnthropic stop_reason: "refusal"; or a turn with no tool call (prose only, empty, off-task)The harness appends a fixed nudge ("No tool call received — you must act via tools; call get_observation if unsure") and continues. The episode runs to its caps and is scored as a failure if it never succeeds — never selectively retried. Retrying only the trials that derailed would be selection bias in the model's favor.
API failureHTTP 429 / 5xx / connection error / timeoutRetry with exponential backoff + jitter (bounded attempts). If exhausted, the trial is marked infra-failed: it is rerun whole (same seed, fresh episode), the rerun is logged in the results JSON as an infra rerun, and infra failures are reported separately from model failures — they say nothing about the model.
Sim-side fault (render error, physics NaN)Harness exception outside the model's controlInfra path, same as API failure: log, rerun whole, report separately.
The line between "model failure" and "infra failure" is drawn at agency. If the model could have acted differently (bad tool call, refusal, wandering to the turn cap), the trial is a scored model failure. If nothing the model emitted caused the fault (network, GPU, kit), it is infra and the whole trial reruns. This line is what makes the N=4 per-model numbers honest.

9. Prior-art anchoring

Four systems anchor this design. MapGPT (Chen et al., ACL 2024; github.com/chen-judge/MapGPT) showed that rendering a topological map into the prompt — numbered place nodes, explicit adjacency, and an agent-updated plan carried across turns — beats raw history for vision-language navigation; we adopt its map grammar (§5.2) and plan carry-forward (§6.5) wholesale, but where MapGPT's map comes from an oracle discrete navigation graph, ours is authored entirely by the model. CogNav models object-goal navigation as an LLM-driven cognitive state machine (broad search → contextual search → candidate verification); we borrow it as prompt doctrine rather than code (§6.3). "Constructing coherent spatial memory in LLM agents through graph rectification" (the LLM-MapRepair line of work) demonstrates that LLM-built maps accumulate structural errors — duplicate nodes, wrong edges — that compound unless explicitly repaired; that finding motivates both correct_position and our decision to log every correction and graph edit for post-hoc audit rather than assuming the map is sound. Finally, Anthropic's embody experiments used an explore_report-style debrief to probe what the model actually retained; our post-episode layout QA (5 fixed questions answered from the model's own map, scored against the layout ground truth) is the direct descendant of that idea. sources: all four URLs fetched 2026-07-26, HTTP 200; arXiv titles verified from page <title> tags — see §11

10. What we predict will fail (honest)

  • Revisit loops. The paper's headline negative result. Even with the map re-injected, a model that mis-asserts set_current_room once can walk a corridor twice believing it is new. Instrumented via: map-accuracy metric (room node precision/recall + adjacency edge accuracy vs the layout ground truth) and the breadcrumb trail, which makes physical loops visible even when the model's map denies them.
  • Hallucinated exits and phantom rooms. A 90° FOV frame of a shadowed corner can read as a doorway; mark_exit makes the hallucination durable, and frontier scoring (§6.4) then actively steers the robot at a wall. Instrumented via: map precision (invented rooms/edges lower it), bump counts clustered near hallucinated exits.
  • Drift mis-anchoring. The failure the graph-rectification paper predicts: the model "recognizes" the wrong landmark (two rooms share a similar rug) and calls correct_position to a wrong anchor — a correction that increases error and can corrupt subsequent mapping. Instrumented via: the correction log cross-referenced post-hoc with true pose at each correction turn (did |error| shrink or grow?), reported alongside the goal-time drift metric.
  • Doorway attrition. Not a memory failure but a compounding tax: 0.35 m doorways vs a 0.16 m body with dead-reckoned lateral error means repeated bumps; each auto-stop costs a turn to recover. Instrumented via: bump counts per trial and time-to-kitchen.

All four are report material either way: the point of the benchmark is to measure exactly these behaviors across models, not to engineer them away.

12. Open questions

  • Does return_home run after a stage-1 cap-out? Current design: no (only after declare_done); a capped stage 1 scores both stages as failures. Defensible but debatable — owner sign-off needed before scoring is unit-tested.
  • Does GPT 5.6 sol accept temperature=0? Unverified (§11): OpenAI's recent reasoning-model families (o-series, gpt-5 lineage) reject non-default sampling parameters, and GPT 5.6 sol is post-cutoff. A one-call probe before the config freeze settles it. If rejected, the OpenAI adapter drops the parameter and §7.1 is reworded to: no provider supports deterministic decoding for the locked models; reproducibility rests on sim seeds alone.
  • Anthropic-side nondeterminism. With sampling parameters rejected and thinking always on (Fable 5), the two Anthropic models are not deterministic at fixed seed. We accept and document this (fixed seeds control the sim, not decoding) — but should the report include a same-seed repeat run to quantify decoding variance? Costs one extra trial per Anthropic model.
  • Motion-tools-per-turn cap. Multiple tool calls per turn are allowed (§3.3). Should the harness cap motion tools at one per turn to keep "one look, one move" cadence, or is chaining (turn_to_heading + move) legitimate efficiency? Currently uncapped; smoke test will show whether chained motion without an intervening observation causes blind bumps.
  • look_around render path. Virtual camera-mount rotation while paused is declared, but the Isaac Sim implementation (rotating the camera prim + 4 renders without stepping physics) needs the smoke test to confirm no frame-latency artifacts (stale frames after teleporting a camera are a known renderer gotcha). Owned by the camera & observation design doc (Doc 04 §5.3); flagged here because look_around's semantics depend on it.
  • First-turn image aging. Policy says images older than K=10 turns are dropped, and the kept first turn loses its image too. Is the spawn-point image worth pinning permanently (helps return_home re-recognition) or is that scaffolding the model should replace with its own map? Currently: dropped, per the uniform rule.
  • Per-model image token cost. 512×512 frames price differently across the three models (and look_around sends four). The cost accounting (§7.1) needs measured per-image token counts from the smoke test before the batch budget is finalized; configs/models/*.yaml files themselves are not yet written.
